## 1. Executive summary
This document defines the technical architecture of **Zobik**, formalizing the move from a centralized orchestration model (rigid graphs) to a dynamic **Compound AI System** built on an **Event-Driven Architecture**. The goal is to create an autonomous, highly scalable AI Swarm, with dynamic cost optimization and resilience to systemic or LLM failures.

## 2. Base architectural pattern
The system abandons monolithic control and rests on the **Blackboard** and **Publish/Subscribe (Pub/Sub)** patterns. No node acts as a master controller; instead, every node acts independently (*Workers* or *Consumers*), reacting asynchronously to the events emitted on a central Event Bus. Each node selects itself through a two-layer matching: topic subscription and semantic similarity of embeddings (see §3.7).

In one pass, the cycle is this. An external request enters the network as a **task announced on a topic** (§3.7.7). The nodes subscribed to that topic decide on their own whether to propose (§3.7.2); an arbiter awards a single proposal atomically (§3.1) and the winner works under a lease it must renew. When it finishes it publishes its result, which can in turn announce subtasks on other topics (§3.9.1). Nobody assigns work: each task exists on the Bus until some node claims it, or it goes vacant (§3.13.2).

### 2.1. Roles vs. nodes: minimal components of the network

The network is made of **nodes**: independent units with a bounded external contract—the topic they claim, a capability embedding with which they compete for the tasks announced there (§3.7.3) and a vocabulary of events they emit (§3.8)—implemented as an Integration Sidecar plus a Logic Container (§3.6.1). How a node solves internally the task it wins is not the network's concern (§2.2). The network is agnostic to which nodes make it up: its behavior does not depend on any particular node existing, but on *some* node existing that claims each published task.

**A node claims a single topic**, and that topic is its entire specialty. It is an invariant of the network and not a style convention; the degenerate case—a purely requester node, which claims none—is admissible, the case of two is not.

On that basis, everything the network needs falls into one of two categories. **Structural** means one thing only: **it is deployment infrastructure**. It comes up together with the network and the network never instantiates it on demand. Its complement is the **emergent role**, which the network creates on demand if needed and which may simply not exist in a given instance.

The criterion that separates a structural component from an external dependency—the ones that are consumed and not deployed, further down in this same section—is **who deploys it**: if it has to be brought up to have a network, it is structural; if it already comes with the platform the network runs on, or is contracted outside, it is not.

Each structural component carries its **category** in italics. The category adds no new rules: it names in the row what the axes further down develop (participation in the Bus, the Spawner's authority, partitioning), and it is what makes this list, the glossary's (§4) and the cold-start one (§5.1) derivable from one another. The list of structural components is:

* **Bus**—*substrate* (§3.6.4–§3.6.5, §4): the pub/sub substrate over which every event travels; without it there is no network to observe and no task to announce. Its contract—subscription model, ordering, retention, topic naming—lives in §3.6.5, and its delivery guarantees in §3.6.4.
* **`intake`**—*fixed-convention topic* (§3.7.7): the entry topic through which every external request arrives, existing by definition in any instance of the network and regardless of which domain nodes are deployed. It is the common entry point: any external request lands there without the Entry Node having to classify it. Whoever claims it through the normal self-selection mechanism (§3.7.5) is, in practice, the first domain node that decides what to do with it—typically decompose it and dispatch subtasks toward more specific topics (`coding`, `testing`, or whatever the network has). Its full contract, together with that of the other fixed-convention topics, is in §3.7.7.
* **Entry Node** (User-Proxy, §3.5, or equivalent)—*structural node*: receives the external request and publishes the first `task.announced` on `intake` (§3.7.7)—it never decides a domain topic, because it is deterministic (§3.6.3) and that classification is a semantic decision that is not its to make. It serves the `hitl_contact_user` audience (§3.5.3), and through it delivers to whoever made the request the outcome of their trace (§3.5.4). Without it nothing comes in and the network sits idle.
* **Operator Channel**—*structural node*: the node the deployment brings up serving the `hitl_contact_operator` audience (§3.5.3). It is a different function from the Entry Node's, even though in the single-user case (§2.4) the same channel reaches both—the same CLI, the same chat window: the entry one opens traces, this one authorizes them. A shared channel does not make them a shared node: they are two audiences, and therefore two topics and two nodes. Every decision the network cannot make on its own ends up here, and §3.17.1 lists all of them. The operator can add channels of their audience, which answer those queries and do not sign acts (§3.14.2). **The enumeration is literal, not aspirational:** all those paths are opened by a structural component that always exists, none depends on an emergent role having proposed, and the notice that accompanies them is a broadcast that obliges no one (§3.8.2, §3.15.2, §3.15.7). It is structural for a reason stronger than availability: **its authority cannot originate inside the network** (§3.14.2), so no component can mint it if it is missing. Without it the network does not stop—each of those circuits has its conservative way out—but it always takes the prudent option without anyone finding out; and its failure is, by construction, the only thing the network cannot report, because reporting it would require the failed channel. That does not change, and it is **the only dependency of the mandatory path** of those decisions, which otherwise depends neither on nodes that may not exist nor on the current vector space (§3.7.7). That is why watching it belongs to the deployment platform (§3.14.1), not to the network. Its full contract—what it authorizes, what it does not, and what administration capability it must implement—lives in §3.17.
* **Spawner**—*structural node* (§3.13): the only authority over which emergent nodes exist—it creates them on vacancy, archives or replaces them according to their quality, and signs the credential with which they compete.
* **Config Store**—*structural node* (§2.3, §3.14.4): holds the Global Configuration—the immutable snapshots of the `versioned` region and the state of the `mutable` one—and is the only one that writes it. It claims the fixed-convention topic `config_change` by deterministic routing and never by auction, like every structural component that owns a topic of that kind (§3.7.7). It is what lets a freshly deployed network be administered before it has resolved its first request (§5.1): **administering the network cannot depend on the network being populated.**
* **Tracing Collector**—*structural node* (§3.2, §3.10): reconstructs traces by passive observation and, over that same aggregate by `TraceID`, enforces the anti-abuse budget (§3.15). It claims `trace_query` (§3.10) by deterministic routing, just as the Config Store claims `config_change`. It is structural because of the enforcement: its absence does not prevent assigning tasks, but it removes the network's spending ceiling without anything signaling it (§3.15.7).
* **Task Broker**—*protocol service* (§3.1): arbitrates the `task.proposed` and grants `task.assigned` atomically. It participates in the Bus by consuming events, but never claims tasks or emits events of its own—it is an arbiter on the critical path of every assignment, and §3.15.7 fixes why it does not take on a second purpose.
* **Network Monitor**—*protocol service* (§3.12): computes the node quality that feeds the Spawner and watches the state of the network—which partitions have enforcement coverage and which do not. It observes the Bus and emits (`node_review`, and toward the operator when a partition loses coverage, §3.15.7), but never claims a task: it notifies, it does not enforce.
* **Context Store**—*off-Bus service* (§3.4): holds the heavy context referenced by Claim-Check. It claims no topic and emits no events—each node's Integration Sidecar queries it on the node's behalf, off the Bus.
* **Contention Registry**—*off-Bus service* (§3.15.2): holds the per-trace freeze and the coverage leases of budget enforcement. It is structural for the same reason as the Context Store, and its contract is explicit for an additional reason that §3.15.2 states—**it is a declared interface, not private state of the Tracing Collector**: the Tracing Collector and the Network Monitor write it (§3.12.1), and the Task Broker reads it on every admission (§3.15.3), besides those who write it. Without it there is no spending ceiling to enforce, even if the Tracing Collector is alive.
* **Specialty Catalog**—*off-Bus service* (§3.13.3, §3.7.6): the library of blueprints (active and archived) plus the Topic Registry. §3.13.3 defines it with the "same role as the Context Store, but for specialties already built": a store shared among all partitioned Spawner instances. It is a condition for the Spawner's existence—without it there are no blueprints to provision and no topic deduplication is possible (§3.7.6)—and its content persists beyond the lifecycle of any instance.
* **Admission Scanner**—*off-Bus service* (§3.14.1, §3.13.3): runs static analysis on an artifact—embedded secrets, credentials, injection patterns—and emits the `scan_result` with which that artifact is admitted. Deterministic and zero-cost in tokens, it rules on **what got baked into the image** and never on what the node will be able to do, which is a matter of boundary and not of content (§3.16.3). It is structural because its absence degrades nothing visibly: without it no artifact is registered, and without a verdict no provisioning passes its precondition (§3.13.1). **There is one per tenant, and the Catalog invokes it in the act of registration** (§3.13.3): what it checks is the artifact's security, which holds equally for every network of the tenant, and the verdict is stored by the digest of its `artifact_ref`, so an image is analyzed once. The artifact's compatibility with each network is a different check, and the Spawner does it when provisioning, together with the verdict's freshness (§3.13.1). Everything that enters the Catalog passes through it: what a Forge derives, what is imported from a Shared Catalog (§3.13.6) and what the deployment seeds.

The classification says nothing about how much the network degrades if a structural component goes down; it only says it is always deployed. What is lost in each case is documented where each mechanism lives (§3.10 for observability, §3.15.7 for cost containment).

**External dependencies: consumed, not deployed.** Closing the *who deploys it* criterion, there are pieces the network depends on that are nonetheless not structural, because whoever operates the platform already provides them or contracts them outside. They do not get their own bullet above, and in §4 they are labeled as such:

* **Embedding Model** (§2.3, §3.7.3): generates the capability, task and topic embeddings. The network reaches it through egress, like any external API (§3.16.3): whether it is a hosted provider or a runtime the person brings up on their own, it is the destination of an `egress_registry` entry. Its selection is a Global Configuration parameter, not an instance the network brings up.
* **Tracing / APM backend** (§3.2, §4): receives what the Tracing Collector exports. It is a dependency of export and of `trace_query` (§3.10), never of enforcement, which §3.15.2 deliberately persists in the Contention Registry so as not to couple it here.
* **Orchestrator and its Active Node Registry** (§3.11): the deployment platform on which the Spawner provisions and decommissions nodes. Nobody installs it *for* the network.
* **Image registry** (§3.13.3): resolves the content-addressed `artifact_ref` of each blueprint. It retains the image of every registered entry until the operator deletes it (§3.13.8), and an image no entry names only for a window the deployment sets.
* **Deployment secret store** (§3.16.6): resolves the `credential_handle` values with which the Integration Sidecar obtains the credential for an egress destination or an ingress source, and the `verify_handle` values with which it verifies the sender of an ingress message. Whoever operates the platform provisions it, by the same criterion with which §3.14.1 delegates transport identity to them—and that is also why the secret stays outside the Global Configuration (§2.3).
* **Egress destinations and the source of their rates** (§2.3, §3.16): the services nodes reach through their Integration Sidecar, and the source of the price at which each call is valued. Whether that source is a table the operator maintains or a service that publishes it makes no difference to the network.

The *who deploys it* criterion is the only thing that decides which side each piece falls on, not the function it serves: the Active Node Registry is an external dependency and the Specialty Catalog is structural, even though on both **the Spawner is the only one that writes what belongs to it** (§3.11, §3.13.3). The reach of that exclusivity is not the same in both, and the difference is that of the two acts of §3.13.3: the Spawner writes the Registry **entirely** and alone, because it describes what runs; of the Catalog it writes **the row qualified by its network**, and the half without a qualifier—the artifact—has other legitimate writers, namely those who build it or bring it in (§3.13.6, §6.5). Reading, on the other hand, is exclusive to no one—the Network Monitor reads the Registry for the usage-axis roster and for the census (§3.12.1, §3.12.3), and the Spawner itself exposes the Catalog through `node_catalog_query` (§3.13.3).

**Participating in the Bus is a separate axis.** The list above is deliberately heterogeneous: it enumerates everything the platform brings up, and the category of each row says *what* each thing is. A **structural node** is a node in the strict sense of the beginning of this section, with the sole caveat that some claim their topic by deterministic routing instead of competing with an embedding. A **protocol service** participates in the Bus without ever claiming tasks: the Task Broker consumes and arbitrates without emitting, the Network Monitor observes and emits without claiming. An **off-Bus service** lives entirely outside it: it is queried through its own interface, and neither publishes nor consumes events. The category is named for what defines it—not participating in the Bus—and not for holding state, because not all of them hold it: the Context Store, the Contention Registry and the Specialty Catalog are stores, and the Admission Scanner keeps nothing; it only answers about an artifact it is given. The distinction matters because several rules hang on the word *node* and do not apply to the other categories: the Spawner is the only authority over which emergent nodes exist and evaluates, archives and replaces them (§3.13); every node competes by similarity (§3.7) with a signed credential (§3.14.2). None of that governs the off-Bus services, which compete for nothing and whose availability the deployment guarantees, just as with the Bus (§3.14.1).

**Observing is not acting: the passive axis.** Some components receive no report: nobody communicates their state to them; they **re-derive it by observing the Bus**—the Tracing Collector reconstructs spans and accumulates cost per trace (§3.2, §3.15.2), the Network Monitor computes the quality signals per node (§3.12.1), the Spawner counts vacancy rounds (§3.13.2). Being passive means exactly that and nothing more: **it does not invent facts**. It does not imply not emitting—all of them emit—or not enforcing anything—the Tracing Collector enforces the budget (§3.15), the Spawner archives and replaces nodes (§3.13). What it forbids is asserting what it did not observe, or moving an aggregate for any reason other than an observation (§3.15.1). It cuts across the categories above and is not one more category: there are passive components among the structural nodes and among the protocol services, and being passive in how state is acquired says nothing about each one's authority, which is defined where each mechanism lives.

**One node, one topic: claiming is not touching.** The invariant at the beginning of this section is stated over *claiming*. A node emits as many events as it needs on other topics when it acts as a requester (§3.9.1)—the Entry Node injects on `intake` without claiming it (§3.5.1), the Operator Channel emits `config_change` and `node_query` without claiming them (§3.17.1)—and none of that makes it multi-topic: what the rule forbids is **competing for tasks of two topics**.

Some things that would not otherwise hold together depend on this. The Spawner's ownership is per topic (§3.13.1), so a two-topic node would have two lifecycle owners, able to archive and replace it for opposite reasons over niche state that neither of them shares (§3.13.3, §3.13.5). And Layer 1 of the matching (§3.7.2) presupposes that subscribing to a channel is a declaration of nature, not a list. **If a channel or a capability has to cover two topics, they are two nodes**—how they are provisioned is the Spawner's business (§3.13), not the network contract's.

**Being a node is not being under the Spawner's authority.** Of the list above, the Entry Node and the Operator Channel are nodes in the strict sense: they claim a topic, emit events and compete through the CNP cycle like any other—by credential and audience membership, because the topic each one claims is a `hitl_contact_*` (§3.7.5, step 4). What does not govern them is the lifecycle: the Spawner did not create them, does not archive or replace them (§3.13.1, §3.13.4) and does not sign their credential either (§3.14.2); the remedy for a degraded one is the operator's, through the deployment platform (§3.14.1), just like its liveness. The boundary needs no list of exceptions in any component: each Spawner mechanism leaves the structural node out by construction, and each one states it where it lives (§3.12.1 for the usage axis, §3.12.3 for the point query, §3.14.2 for the credential). What makes the broad reading unacceptable is `hitl_contact_operator`: archiving that channel would mean the network dismantling on its own the root of trust that §3.14.2 deliberately puts beyond its reach.

**Partitioning is a separate axis.** Being structural does not imply being partitioned—the Entry Node and the off-Bus services are not. Those that are—Task Broker, Spawner, Tracing Collector and Network Monitor—come up already partitioned by consistent hashing over the full space of possible `topic`/`TraceID` (§3.1, §3.10, §3.13.1, §3.12.1), from the network's start and before any concrete domain topic exists. How many partitions each one has is neither a fixed nor a configured number: it is derived from the live membership of the substrate and grows and shrinks with load (§3.19). That is why a freshly deployed network, with no worker yet, already has a Spawner owning any topic that comes to exist—including `intake` from the first second.

### 2.2. Free internal complexity: the system does not see inside a node

The network neither imposes nor knows anything about how a node internally solves the task it won. A node can be as simple as a single LLM call, or as complex as a traditional agent loop with retries, self-evaluation, its own tools or multiple refinement passes before publishing a result—the network does not know and does not need to know. The only thing the system knows about a node is its **external contract**: the topic it claims—only one, and it is its whole specialty (§2.1, §3.6.5)—the capability embedding with which it competes (§3.7.3), and the vocabulary of events it emits (§3.8). The Spawner fixes that contract when it creates the node (§3.7.1), precisely so that it is clear what kind of tasks it can solve, without that restricting *how* it solves them internally.

A direct consequence: the system does not determine cycles, retries or escalations of any kind either. If a node emits a task and receives a `task.failed` or `task.rejected`, the decision of what to do—retry internally, reopen the task to the network, escalate, ask for human help, or simply give up—is exclusively its own. The exception is the subtask left outside the current vector space, which the Integration Sidecar reopens because the failure is the network's and not the task's (§3.3). See §3.3 for the development of this idea and §3.9 for its implications when a node depends on subtasks of its own.

**Corollaries.** They follow from the above:

* **The internals are neither inspectable nor enforceable.** A `task.completed` is an assertion by whoever emits it, not a proof the receiver can verify. No external mechanism—platform identity, signed credential, Task Broker verification—makes up for that lack: they all settle who is speaking and with what permission, not what it did. The only things the network sets against that risk are each requester's local trust (§3.9.2) and the quality signals observed from outside (§3.12).
* **Nor are the internals interruptible.** The system cannot stop the work of a node that already has an assigned task: a current lease runs its course until `task.completed`/`task.failed`. The only thing that can be stopped without breaking the boundary is the *admission* of new tasks, and every cancellation signal is cooperative—it is offered, not required (§3.15.3 for both).
* **The network does not guarantee that something happens.** It distinguishes a task nobody claimed (§3.7.5) from one someone claimed and could not carry out (§3.3), and it has no notion of a request closed without producing the effect someone expected: having it would require an object that declares the expected result, and no component holds one (§2). A node that concludes it should act and closes with `task.completed` without announcing the subtask that produces the effect leaves a complete trace and an unfulfilled request—and that trace is **indistinguishable** from that of a node that legitimately solved an atomic task without subtasks of its own: no signal inside the network separates the two cases (not even the per-task log, §3.10). The only things set against it are its requester's local trust (§3.9.2) and, at the root, the person on the other side (§3.5); concretely, the only detector is a reopen by whoever expected the effect and did not see it—external to the network and conditional on someone noticing the absence. The guarantee that does hold is the complementary one: nothing with an effect outside the substrate happens without authorization (§3.16).

### 2.3. Global Configuration: the shared parameters of the system

Besides the external contract each node exposes (§2.2), the whole network operates under a set of shared configuration parameters: constants that belong to no particular node, but govern the aggregate behavior of the system. They live in a single configuration source—not in the code of an individual node nor in the payload of any event. An initial version is provisioned with the network's deployment, and from then on only the operator modifies it, through the path of §3.14.4.

This Global Configuration defines no new mechanisms; the mechanisms are already fixed in the rest of this document. What it contributes is the concrete *value* of the parameters those mechanisms leave open to calibration. The list is not closed—any parameter of that kind belongs here, not in the architecture document—and it enumerates those of the mechanisms this document fixes. Those of the Spawner's decision strategy (§3.13.4) and those of the Network Monitor's trigger logic (§3.12.3) live in the same schema, declared by the logic that consumes them. It includes at least:

* Default similarity floor with which a node is provisioned, `task_similarity_floor` (§3.13.3). The floor with which a node actually proposes is the `similarity_floor` of its credential (§3.14.2), and this parameter is the value the Spawner assigns to an entry that never ran on this network—derived, imported or seeded. One that already ran comes back with a floor from its history (§3.13.3). It is not a one-off choice at derivation: from that initial value, the lifecycle's exploration moves it (§3.13.4). **No component reads it when admitting a proposal** (§3.7.5, step 4).
* Lifetime of an unrenewed task lease, `task_lease_ttl` (§3.1): how long the Task Broker tolerates receiving no renewal from the assignee before returning the task to `UNASSIGNED`. It does not measure how long a task can take—that would make it incompatible with §3.9.1—but how long the network takes to notice that its assignee is no longer alive, and both crash recovery and the Spawner's no-signal return (§3.13.2, missing-coverage branch) hang on it.
* Auction duration, `auction_timeout` (§3.7.5, step 5): how long the Task Broker waits for proposals on a `task.announced` before declaring the task vacant. Together with `reannounce_backoff_base` (§3.1) and `vacancy_rounds_threshold` it determines how long the Spawner takes to intervene on a vacancy, so they are calibrated together. It is also what makes a `hitl_contact_*` round nobody takes cheap (§3.5.2): **the schema declares the precondition `auction_timeout < hitl_response_window`**, because that section's argument—that a round with no enabled channels costs an auction timeout and not a human wait window—stops holding if the order is reversed.
* Task Broker re-announcement backoff (§3.1, which fixes its shape): `reannounce_backoff_base`, the initial interval between successive re-announcements of the same task, and `max_reannounce_backoff`, its ceiling.
* Threshold of vacancy rounds that triggers the Spawner's intervention, `vacancy_rounds_threshold` (§3.13.2).
* Retry backoff for the Catalog's embedding regeneration, `embedding_regeneration_backoff` (§3.13.7): it keeps an unresponsive model from turning the repair of the vector space into a cycle of failed calls. Once the backoff runs out without success, the Spawner warns through `network_risk` (§3.15.7).
* Selection of the network's vector space, `embedding_model` (§3.7.3, §3.7.4). It has a **composite shape**: the `egress_registry` entry through which the Embedding Model is reached (§3.16.3), the model requested from it and the task-prefix convention with which both halves of the matching are generated. **It has no default value:** the network is born without a vector space, and the precondition further down keeps it paused until the operator assigns it (§5.1). The `model_id` is not a field of this key but the identifier each generator derives from it (§3.7.3); it travels in the payload and in the signed credential because the Task Broker compares it before recomputing a similarity (§3.7.5, §3.14.2). It is the only parameter in this list whose change is not calibration but a redefinition of the space in which everything else is compared; what makes it an executable change instead of an irreversible one is the persistence rule of §3.7.3, which makes every embedding a recomputable derivative of a stored text, and the procedure of §3.13.7, which orders its execution. **Structural proposers are deliberately left outside that blast radius**, because their admission does not go through similarity (§3.7.5, step 4): otherwise this parameter—editable by `config_change`—could make inadmissible the Operator Channel, which is precisely the one that authorizes every `config_change` and the only thing the network cannot re-issue (§3.14.2), and the Spawner itself, which is the one that runs the migration.

  **It belongs to the current class, field by field.** The only component that *compares* two vectors—the Task Broker—**does not read this parameter at all**: step 4 of §3.7.5 checks the credential's `model_id` against that of the `task_embedding`, both arriving in the event, in a relational check and not against a configured value. And the components that *generate*—each node's Integration Sidecar when publishing (§3.6.1) and the Spawner when signing (§3.14.2)—each consume it in its own cycle, without having to agree with anyone on a judgment. No pair of components judges the same fact against the config.

  **Nor is it pinned per trace, and the right consequence is the opposite of that of pinned parameters: here the change has to reach everyone immediately.** A pinned trace would keep generating embeddings of the old space against an already migrated fleet, and its vacancy would be permanent instead of transient; that is why the procedure of §3.13.7 can treat the population of stale tasks as a finite queue that drains itself.
* Similarity comparison precision, `similarity_precision_decimals`: the number of decimals to round to before checking against any of the floors, so that the node's computation and the Task Broker's recomputation do not differ at the edge (§3.7.5). Embeddings are stored and signed normalized, so the cosine reduces to a dot product. **It plays a double role, and deliberately with a single value:** besides fixing the edge of the floors, it defines the granularity at which two proposals count as tied and enter the award draw (§3.7.5, step 4). A single value is what keeps both readings consistent: two nodes tied at that granularity are also tied with respect to the floor, and the network does not assert about them a resolution it has already declared it does not have.
* Observation window (`quality_window`), minimum observations before being actionable (`min_observations`), evidence staleness bound (`evidence_staleness`) and the deferred-classification `grace_period` of the node quality score, plus the action threshold on that score, `score_floor` (§3.12.1, §3.13.4). `score_floor` is **the constraint of the network's objective function** (§3.12.2): each node's `margin` is measured against it, and its violation is what `low_score` asserts (§3.12.3).

  **`quality_window` is declared in the node's observations and not in time**, and `evidence_staleness` is the axis's only wall-clock magnitude: it bounds how old the evidence entering the window can be, without sliding it (§3.12.1). `quality_window` and `min_observations` also carry a schema precondition, `min_observations ≤ quality_window`—a ceiling below its own floor leaves every node permanently unevaluable, and silently.

  **The ratio `min_observations / evidence_staleness` is, moreover, a minimum flow per niche** (§3.13.5, §3.13.9): calibrating it too high for the network's real traffic leaves entire niches below the threshold the lifecycle needs to act on them—not one problematic niche but the **entire** blue/green inoperative, silently. No mechanism is needed to detect it: the flood of `niche_uncoverable` is the signal, the same argument by which §3.13.5 rejects a global cap on the vacancy fan-out. What belongs here is calibrating both parameters against the network's real traffic and not against a reference value.
* Outer fraction of the radial axis, `outer_share` (§3.12.2): what fraction of the `quality_window` tasks—those with the lowest similarity to the node—forms its outer group. The schema declares its range as `(0, 0.5]`, because the outer group is the edge of the radius and never the majority of its tasks, and the precondition `min_observations ≤ outer_share · quality_window`: with a smaller fraction, the outer group never reaches `min_observations` and no node narrows.
* Unit in which `cost` is denominated in `data.metrics`, `cost_unit` (§3.8.1, §3.10): a single fixed unit per network deployment—typically a currency code such as `USD`, but the schema does not fix it—into which each node's Integration Sidecar converts what each provider bills, because aggregations across nodes (`spend_window`, §3.12.1) and across traces (`budget:<TraceID>`, §3.15.1) add up quantities from different nodes and stop making sense if they do not share a unit.
* **`egress_registry`** (§3.16), the counterpart of the previous key—the unit in which its rates are denominated. One entry per egress class the network has authorized, with the operation interface it implements, the `target` and the `operations` that define it, the `grant_scope` that fixes which nodes reach it, the `credential_handle` with which its credential is resolved—never the secret, which deliberately lives outside (§3.16.6)—and the `credential_placement` that fixes where it goes in the request, the `rules` that decide, by the operation and the fields of each call, whether it runs, is denied or is approved by an audience, the `billing_rule` with which the Integration Sidecar extracts the billing data from a response (§3.10) along with the `rate_source` the rate comes from and its `as_of`, and the `max_body_size` that bounds its bodies. It is the only key in this list against which every exit from the substrate is resolved, and its full contract lives in §3.16.

  **It declares where the rate comes from, not the rate.** That is what lets a deployment maintain it by hand or refresh it against an automatic source without either form changing anything in the contract: choosing the source is a configuration edit and goes through §3.14.4; the values behind it moving is not. An old `as_of` is the sign that the rate stopped following the world, and the one who checks it is the operator, on their own configuration—an outdated rate on the low side underestimates spending without anything else giving it away.
* **`egress_lists`**, the lists of values that the `egress_registry` rules read (§3.16.2): each with its name and a set of scalar values—allowed recipients, blocked beneficiaries. It is the only `mutable` key in this list (see the region further down), because such a list is usually personal data and the operator edits it element by element.
* **`ingress_registry`** (§3.16.7): one entry per ingress class the network has authorized toward its channels, with the interface it implements, the `listener` where it listens or the `source` the channel connects to in order to fetch its messages, the `operations` it admits, the `verify_handle` with which the sender is verified or the `credential_handle` with which it gets into the `source`, the `rules` that admit or reject each message by its operation and its fields, and the rate, size and pending-message ceilings. Its full contract lives in §3.16.7.
* Parameters of the Network Monitor's `node_review` emission queue (§3.12.1): `review_emission_rate`, the cap on reviews an instance emits per window in its partition, and `exploration_share`, the fraction of that flow reserved for routine triggers; why the queue carries a cap and a reserve lives in §3.12.1. **`exploration_share` is the network's explore/exploit dial**, and it is the only parameter in this list that expresses how much the network is willing to invest in improvements no measurement asked for.
* Exploration parameters of the blue/green cycle (§3.13.4, §3.13.5): `max_concurrent_exploration`, the cap on simultaneous exploratory candidates per partition, so that a streak of routine reviews does not double the active fleet; and `max_candidate_maturation`, how many assignments on its topic a candidate can let pass without reaching `min_observations` before the Spawner declares the trial expired (§3.13.5). It is denominated in opportunities and not in time, like every deadline that measures whether a node made use of the occasions it had (§3.12.1).
* Opportunity window of the usage axis, `usage_window` (§3.12.2), declared in assignments granted on the node's topic and independent of those of the score because it measures usefulness and not quality (§3.12.1). There is no minimum-age parameter: an incomplete opportunity window already expresses that the node has not yet had occasion to win anything.
* `win_rate` cutoff with which the Spawner resolves a `low_usage`, `high_win_rate` (§3.13.4): below it, the node proposes and loses, and is archived; at or above it, it wins the little it proposes, and its floor is widened. **The schema declares its range as `(0.5, 1]`**, because replacing a node with its widened candidate depends on losing half of what it proposes never counting as a high `win_rate`.

  **Each node-lifecycle magnitude is declared in the unit of the cause that moves it, and few are temporal** (§3.12.1, where the rule lives and what is denominated in each currency). Those that remain denominated in time are evaluated against the `admission_clock` of that same section and not against wall-clock time; the exception is `evidence_staleness`, which bounds the age of a datum and not the merit of a node.

  **All node-lifecycle parameters belong to the current class**, by the test at the end of this section: the Network Monitor and the Spawner each consume them in their own cycle, and no pair of components has to agree when judging the same fact against them. The argument holds for the whole family—those already there and those added later—but what classifies each parameter is still its own declaration in the schema, not this sentence.
* Range of **Node Runtime Interface** versions the deployed Integration Sidecar supports, `runtime_interface_range` (§3.6.1). Unlike the rest of this list it is not a calibration but a **declaration about the substrate**: it is provisioned together with the Integration Sidecar itself and describes which Logic Containers it can host. The Spawner reads it as a precondition before provisioning or reviving a blueprint (§3.13.2, §3.13.6), so that the incompatibility fails early and with a readable reason instead of showing up as a node that does not start. Its being a declaration and not a guarantee is precisely why the real enforcement does not live here: the Integration Sidecar rejects on its own a Logic Container outside its range, so an outdated config produces a provisioning that fails, never an incompatible node competing (§3.6.1).
* Neighborhood similarity floor between capability embeddings, `agent_similarity_floor`, used by the Spawner to evaluate coverage redundancy (§3.13.4)—distinct from the floor with which a node proposes for a task (§3.7.5). The identifier keeps the `agent_` prefix for compatibility; the population it compares is node capability embeddings (§3.7.3).
* Neighborhood similarity floor between topic embeddings, `topic_similarity_floor`, used by the Spawner to avoid minting a redundant topic when creating the first node over a vacant task (§3.13.2, §3.7.6)—distinct from `task_similarity_floor` and `agent_similarity_floor`, because it measures overlap of channel purpose, not task fitness or node coverage redundancy.
* The snooze periods the Spawner applies to a node when closing a review, before the Network Monitor evaluates it again (§3.13.5): `node_review_snooze`, short, when there is a candidate maturing; and `no_action_snooze`, deliberately longer, when the review found nothing to do. **They are denominated differently because they wait for different things** (§3.12.1): `node_review_snooze` waits for the evidence the candidate has not yet produced, so it is counted in observations; `no_action_snooze` waits for the world to move, which is a wall-clock fact. `no_action_snooze` **doubles on each successive review closed without replacement, up to the ceiling `max_exploration_backoff`**—which exists so that the backoff does not become an accumulator and leave an old node asymptotically unexplorable, which would be wrong because the improvement frontier moves for causes unrelated to that node (§3.12.1).
* Local reputation floor for promoting a blueprint to the Shared Catalog across networks—`min_observations_publish` and `score_floor_publish`—deliberately stricter than `min_observations` and `score_floor` (§3.13.6).
* Anti-abuse budget thresholds per `TraceID`—`trace_budget_cost` and `trace_budget_reopens`—that trigger the cost-containment mechanism (§3.15.1).
* Budget increments granted by a human decision to continue after `trace_risk`—`trace_budget_extension_cost` and `trace_budget_extension_reopens` (§3.15.6). The size of the extension is network policy; whoever answers the query does not choose it: the human decides *whether* to continue, not *how much*.
* Lifetime of the renewed keys of the Contention Registry, `coverage_lease_ttl`: how long both a Tracing Collector partition's coverage lease and a trace-freeze mark last without renewal (§3.15.7). A generous value relative to the Tracing Collector's renewal interval.
* Network policy when a partition loses enforcement coverage, `budget_coverage_policy`: `fail_closed` (the Task Broker stops admitting new tasks from that partition) or `fail_open` (the network keeps admitting, with no spending ceiling). §3.15.7.
* Cap on successive candidates of the Spawner's blue/green cycle over the same semantic niche, `max_successive_candidates` (§3.13.5).
* Cap on egress authorization requests the Spawner emits over the same niche before it stops asking, `max_egress_requests_per_niche` (§3.16.5).
* Parameters of the nodes' memory reservation (§3.13.10): `default_memory_required`, the reservation of an entry that does not declare `memory_required`; `memory_growth_factor`, by how much the Spawner multiplies the reservation of an entry whose node died from exceeding it; `memory_auto_share`, the fraction of the fleet's capacity up to which it raises it without asking; and `eviction_pressure_threshold` with `eviction_pressure_window`, how many evictions within that window broadcast the capacity notice.
* Lifetime of the Catalog's presence mark, `catalog_presence_ttl` (§3.13.3): how long the mark with which a network declares that it runs an entry lasts without renewal. A generous value relative to the Spawner's renewal interval.
* Fraction of the artifact storage capacity beyond which the Spawner warns that it is filling up, `artifact_storage_pressure_share` (§3.13.3, §3.15.7).
* Wait window for a human response before a `hitl_contact_*` round is declared expired, `hitl_response_window` (§3.5.2).
* How the channel that opened a trace delivers its outcome to whoever originated it, `result_delivery` (§3.5.4): one value per audience and a default one, among `none`, with no query; `ack`, an acknowledgment of receipt; and `acceptance`, an acceptance that allows rejecting the outcome.
* Drain period of a channel being decommissioned, `channel_drain_timeout` (§3.13.8): how long it keeps delivering the outcomes of the traces it opened before closing those it still has.
* Grace window of Context Store retention, `context_retention_grace` (§3.4): how long the context of a `TraceID` survives after all the tasks in its tree have reached a terminal state, to allow post-mortem debugging. The same window governs the closing of an aborted trace (§3.15.6). It is retention of source code and user data, so its value is the instance's privacy policy and not a performance constant—early on-demand deletion does not depend on it (§3.4, §3.14.3).
* Network admission state, `network_admission`: enum `open` (default) | `drain` | `frozen`, read by the Task Broker before granting any assignment (§3.18). It is the only parameter in this list whose effect is not to calibrate the behavior of a mechanism but to **stop the network's work**; that is why its full contract—what is stopped, what is exempt and who reverts it—lives in its own section and not here.

The concrete value of each one is outside the scope of this document: it is a calibration/implementation decision, not an architectural one, and it can change without affecting the design described here. Whoever deploys an instance of the network decides and maintains those values in their Global Configuration.

**The configuration has a declared schema; it is not a list in prose.** Each parameter is declared with a name, a type, an admissible range, a shape (scalar, enum, or a composite entry like those of the `egress_registry`, §3.16.2), a **query class** (pinned per trace or current, the distinction at the end of this section), a **region** in the `storage` field (`versioned` or `mutable`, the distinction further down) and, where applicable, **preconditions on other keys**: a condition the resulting snapshot must satisfy for an edit of this key to be valid. A composite-shape key **declares its class per field**, because an entry can bring together a fact about the world and a rule a trace is judged under, and the test at the end of this section separates them. The schema is what lets an edit be validated without understanding what it means (§3.14.4), and what lets an Operator Channel **generate its administration interface from the declaration** instead of hand-coding the list of parameters (§3.17): a CLI builds subcommands, a panel renders a form, a bot opens a modal, all from the same source. Adding a parameter later does not require touching any channel.

The declared preconditions are: **editing `embedding_model` requires the resulting snapshot to carry `network_admission = frozen`** (§3.13.7, §3.18); **a snapshot with `network_admission` other than `frozen` requires `embedding_model` to be assigned** (§3.18)—without a vector space there is no matching, and an open network would admit work no node can claim; **`min_observations` cannot exceed `quality_window`** (§3.12.1)—a window ceiling below its own confidence floor is a configuration that does not fail but goes silent, leaving every node permanently unevaluable; **nor can it exceed `outer_share · quality_window`** (§3.12.2), for the same reason applied to the outer group; and **`auction_timeout` is less than `hitl_response_window`** (§3.5.2). The mechanism is declared generic, and not as a special case, because of the properties above. It is still structural validation—the Store checks two keys of the artifact against each other, without understanding what changing models means (§3.14.4)—and since it travels in the declaration, an administration channel can anticipate the rejection and offer both edits together instead of letting the person discover the condition through a `task.failed`.

**Immutable, numbered snapshots.** The `versioned` region, where every key lives except those declared `mutable`, is a sequence of versions: each `config_version` is the *whole* state—never a delta—a published version is neither modified nor deleted (the same reversibility criterion with which §3.13.3 treats blueprints), and each one carries attribution of who authorized it **and a publication timestamp**. That timestamp is not decorative metadata: it is what turns the sequence of versions into the authoritative record of *how long* each value was in force, and the Network Monitor's admission clock (§3.12.1) comes from it without needing any new state or any notification channel. Atomicity is per complete snapshot and not per key: nobody ever observes a mix of two versions, and **going back is one more write, not an emergency procedure.**

**The sequence is retained in full, and that is a contract and not an implementation choice.** No published version is discarded for age or for a revision cap: the mechanism that holds the sequence is free, but one that prunes it does not satisfy this section. Two things hang on this that would fail silently and not with an error. The Network Monitor's `admission_clock` (§3.12.1) is a pure function of the sequence of timestamps, so a truncated history leaves it measuring against a past that is no longer there, and the N instances stop agreeing by construction. And a trace in flight reads its pinned `config_version` long after having stamped it (§3.5.1), so discarding old versions expires long traces—exactly the ones pinning exists to protect.

**The `mutable` region holds what has to be deletable.** Its keys are edited per element—adding or removing one—and what is removed ceases to exist: it remains in no earlier version, because the region has no versions. It is where the configuration that is usually personal data lives, which full retention would make impossible to delete, by the same criterion with which §3.16.6 leaves the secret out of the registry. Each edit is attributed—who, when, on which key and with which operation—without the value, because storing it would retain what the region exists to be able to delete. The flip side is that there is no going back: an element removed by mistake is added again by hand.

**Only a current key can be `mutable`, and the schema rejects a pinned one.** What is pinned per trace and what the `admission_clock` reads are what demand the full retention of `versioned`; a current key is always read in its present state, so it needs no history. For the same reason there are no preconditions across regions: a precondition is evaluated over a snapshot, and `mutable` has none. Whoever reads a `mutable` key treats a reference to an element that does not exist as its own error.

**How it is queried: two classes of parameter.** Because the configuration is editable at runtime, two components may be reading different versions at the same instant. **A single test decides the class: if two components have to agree when judging the same fact against the parameter, it is pinned per trace; if each consumer reads it in its own cycle without having to agree with anyone, it is current.**

* **Pinned per trace.** A node rounds its similarity to `similarity_precision_decimals` and the Task Broker **recomputes** its own with that same rounding (§3.7.5, step 4). If they read different versions, the recomputation would differ at the edge of the floor. For these, **the snapshot is part of the trace context**: whoever opens the trace stamps `config_version` in the envelope (§3.5.1) and every child event inherits it unchanged, just like `traceparent` (§2.4). The live cases are `similarity_precision_decimals`, `hitl_response_window` and the budget thresholds and extensions per `TraceID`.
* **Current.** Everything else: it is read from the latest published version—or, in `mutable`, from the present state—without coordination and without notification (nobody subscribes to configuration changes), because a single component consumes it in its own cycle. It is the default class, and by far the most populated: the Network Monitor's weights, windows and queue parameters, the Spawner's entire node lifecycle—including `task_similarity_floor`, `agent_similarity_floor`, `topic_similarity_floor` and the Shared Catalog publication floors `min_observations_publish` / `score_floor_publish`—as well as `vacancy_rounds_threshold`, `embedding_regeneration_backoff` and `runtime_interface_range`, the Task Broker's backoff along with `task_lease_ttl` and `auction_timeout`, `coverage_lease_ttl`, `budget_coverage_policy` and `network_admission`. `embedding_model` and `context_retention_grace` go here too, even though several components consume them, because none of them has to agree with another when judging a fact: the generators read `embedding_model` each in its own cycle and the only comparator does not read it (see its bullet above), and the Context Store and the Tracing Collector read `context_retention_grace` to each retain their own part of a closed trace (§3.4, §3.15.2).

  The `egress_registry` and `egress_lists` pass the same test the same way: the Spawner reads the registry to choose an entry when deriving, and the Integration Sidecar to resolve, price and evaluate the `rules` of the call it mediates, which are different facts, and nobody evaluates those rules again on that call (§3.16.4). The consequence is that of `embedding_model` and not that of a pinned parameter, and it shows on both sides of the entry. **A pinned rate would make a long trace keep accumulating at old prices**, and the running total of §3.15.1 would stop following real spending, which is the only thing that ceiling exists to contain. And **a pinned rule or list would not reach traces in flight**: a beneficiary the operator blocks has to be blocked on the next call, not on the next trace. Loosening a rule also reaches traces in flight, and breaks nothing, because the Logic Container does not know the gate its call goes through. The `ingress_registry` is current by the same test: the Spawner reads it when associating a channel and the Integration Sidecar when admitting each message, and a message arrives before the trace that would pin anything exists (§3.16.7).

**Each parameter's class is declared in the schema, not inferred from these lists.** The names above illustrate the test; they do not exhaust it: the authoritative source is the *query class* field of the declaration, and a new parameter is not classified because someone adds it to a paragraph but because its declaration says so. It is the same as what already holds for type or range, and it has the same practical consequence: each consumer resolves which version to read a key against by looking at its declaration—the envelope's `config_version` always travels already, so pinning costs nothing extra (§3.5.1)—and the administration channel can show the class next to the value without hand-coding any enumeration (§3.17). A parameter without a declared class is an invalid configuration, just like one without a type.

The semantic consequence is the right one: **a change to a pinned parameter applies to new traces, and those in flight finish under the rules they started with.**

**That statement speaks of pinned judgments, not of admission**, and without that nuance it looks like a contradiction with two mechanisms that already exist. What finishes under the rules it started with is the *semantic evaluation* of a trace: which floor a similarity is compared against, how long a human query waits, which ceiling spending is measured against. Whether the Task Broker admits a new task was never part of that—the freeze of §3.15.3 stops traces in flight without going through `config_version`, and `budget_coverage_policy` changes the fate of already open traces as soon as it is published. `network_admission` is one more instance of the same case: it is current, it affects traces in flight deliberately, and it does not break the rule because it touches no pinned judgment.

**What does not live here.** What is deliberately left out is left out for the same reason: it is what a change is validated against, so it cannot be the object of a change.

* **The root of trust**—the deployment root against which the operator's proof is verified, and the credential provisioned with the deployment that signs it (§3.14.2). If it were configurable, a compromised Operator Channel would rotate the root and become irrevocable from outside; with it left in the act of deployment, regaining control is always possible through deployment.
* **The schema itself**—it comes with the deployment, alongside the code that consumes it. If it were editable through configuration, it could be widened to admit an invalid configuration and the validation of §3.14.4 would stop meaning anything.

### 2.4. Scope of a network instance: one user, multiple projects

Each network instance belongs to a single **tenant**—the same model as Claude Code or GitHub Copilot: the Bus, the Task Broker and the Context Store are not shared between different tenants; each one runs its own network instance. This is not a logical-isolation decision (ACLs, `tenant_id`) but a consequence of deployment: no state of these components crosses that boundary, so there is no competition for tasks and no risk of context leakage between tenants to solve at the architecture level.

**A tenant is not a person.** It is whoever deploys and operates the instance—in the development use case, an individual; in that of §5.4, a business. A single instance may have to contact several distinct human populations, with different authority and channels, and none of them is necessarily the tenant: in §5.4 the network belongs to the business and the end customer is an external audience. The network distinguishes those populations by audience topic (§3.5.3), not by person identity—there is no user model inside the Bus, nor any need for one. Strong isolation is still the tenant's; between audiences of the same tenant the separation is one of routing: which User-Proxy serves which topic.

Within that same instance, a user can have several projects/repos open at once, each generating its own tree of `TraceID`s concurrently. This introduces a dimension—which project a task belongs to—that the envelope carries explicitly (`data.workspace`, §3.8.1), inherited by every child event just like `traceparent` (§3.2), so that any node knows which repo/working directory it operates on without having to infer it from the `TraceID`.

Nodes are not partitioned by project: specialization is by capability (§3.7.1), not by task instance or by project, so the same node naturally competes for tasks from any of the user's projects that fall within its specialty—which is desirable, because it avoids duplicating the same node for each repo that falls within its specialty. Since each node hydrates its context by Claim-Check on each individual assignment (§3.4) and keeps no state between tasks, nothing carries over from one project to another.

The Task Broker still partitions by `topic` (§3.1), not by project: if two projects of the same user generate tasks on the same topic at the same time, they compete in the same auction. This is a matter of fairness/QoS between concurrent projects, not of isolation—it is deliberately left without a dedicated mechanism, assuming a low volume of simultaneous projects per user; if the volume justified it, it would be an extension over the existing partitioning, not a new component.

**Specialty Catalog, the exception:** unlike the Bus, the Task Broker and the Context Store, it is not exclusive to a single network instance. Sharing the work of building nodes among the networks of the same tenant is the object's purpose, not one optimization among other deployment options: it is a library of blueprints, not a real-time assignment resource, so sharing it among a tenant's networks creates no competition between them—a blueprint is written once and all of them see it. **"Private" is the tenant boundary, never the boundary between networks of the same owner**: the Specialty Catalog is private by default toward other tenants, and can optionally be promoted to a Shared Catalog across tenants under the governance requirements of §3.13.6—that promotion is the same idea of sharing, escaping the tenant boundary, with the gates that boundary demands.

**There is one instance per tenant, and that is why it is reached through an interface and not by co-residence.** Deploying a tenant's second network points to the Catalog that already exists instead of instantiating another—otherwise the per-network qualifier of §3.13.3 would qualify nothing, the write-if-absent keys that arbitrate provisioning among partitioned Spawner instances would each arbitrate against their own copy, and the Forge could not read what the request references (§6.3). From this follows what those sections already assume without saying it: the Catalog cannot be resolved as a local store of any of its readers, because none shares a host with all the others. The same holds for the registry that resolves the `artifact_ref` (§3.13.3) and for the backend the Tracing Collector exports to (§3.2), for the same reason and with the same scope; §6.1 declares the Forge **local to the tenant**, which is a trust boundary and not a co-residence assumption.

## 3. Solutions to distributed-systems challenges

### 3.1. The Task Broker: atomic assignment and race conditions
To keep multiple nodes from consuming and processing the same task simultaneously, the system implements a **Task Broker (State Registry)** with strict concurrency mechanisms. Internally, the Task Broker keeps for each task a minimal three-position state machine—`UNASSIGNED` (published and without an owner), `CLAIMED` (awarded to a node, with a live lease) and `DONE` (result received, the task leaves the game)—and everything that follows in this section is the transitions among those three:
* **Claiming pattern:** Nodes publish `task.proposed` (§3.8.2). The Task Broker verifies the signed credential that accompanies each proposal (§3.14.2) and does not trust the similarity value the claim declares: it **recomputes** it from the embedding that credential carries and the `task_embedding` it already holds for the task, and awards by that recomputed value (§3.7.5). The value attached in the claim can only lower it, never raise it. The Task Broker evaluates and grants the task through an atomic operation—single-threaded *within its partition* (see horizontal scaling by partition, in this same section); that bound is what keeps it simple, fast and deterministic without turning it into a global bottleneck. The award moves the task from `UNASSIGNED` to `CLAIMED`, and that atomic transition is what guarantees a single winner: claims that arrive later find it already out of `UNASSIGNED` and are discarded with no need for additional coordination.
* **Leases and timeouts:** Each `CLAIMED` task has a lifetime (`task_lease_ttl`, a Global Configuration parameter, §2.3). The happy path ends in `DONE`: the assignee returns its result and the task stops being a candidate for anyone. If instead the whole node goes down (crash/OOM of its deployment unit), the renewal stops arriving, the *lease* expires and the task automatically returns to `UNASSIGNED` to be taken by another worker. If only its Logic Container goes down, the Integration Sidecar closes the task with `task.failed` without waiting for the lease (§3.6.1). `DONE` is the only terminal state; `CLAIMED` can always go back.

  **The TTL is a window without renewal, not the total life of the assignment**, and the distinction is one of mechanism and not of calibration. The assignee **renews** its lease while it keeps working on the task; the Task Broker only expires it when that renewal stops arriving. If it measured total duration, §3.9.1 would break outright: every node that emitted subtasks waits for its children before completing, so in any deep trace the lease of each intermediate node would expire halfway and its task would be re-announced while still in progress. What the lease detects is **the absence of a live assignee**, not slowness—the same criterion by which the Contention Registry's coverage lease declares effective enforcement and not a running process (§3.15.7). From this follows, with no additional mechanism, the way the Spawner "returns" a task without signaling anything: it stops renewing (§3.13.2, §3.13.3).

  **Renewal is a signal from the assignee to the Task Broker, outside the event model of §3.8.** It has no `type` or `traceparent`, and nobody else receives it. It says only that the assignee is still alive, and it counts at the moment it arrives: a renewal is not stored to be delivered later. **Only a task's assignee renews its lease:** the Task Broker discards a renewal whose identity—the one the deployment attributes to it (§3.14.1)—is not the assignee's, and one for a task that is not in `CLAIMED`. Without that check, a live node could hold on to the task of a failed one, and the task would not return to `UNASSIGNED`.
* **Re-announcement with backoff:** each time a task returns to `UNASSIGNED`—because its lease expired or because the auction timeout expired with no proposal above the similarity floor (§3.7.5)—the Task Broker publishes `task.announced` again (same `task_embedding`, reused per §3.7.4) on the same topic. The interval between successive retries grows instead of staying fixed, so as not to saturate the topic while the lack of candidates persists: **exponential backoff**, starting from `reannounce_backoff_base` and doubling it on each successive re-announcement of the same task up to the ceiling `max_reannounce_backoff` (both Global Configuration parameters, §2.3). This single mechanism covers both the case of a failed worker and that of a task that never had any candidate—for the Task Broker they are the same state transition (see §3.13.2 for what the Spawner does with that repeated vacancy).
* **Horizontal scaling by partition (sharding):** the Task Broker is not a single process—it is a set of partitions, each single-threaded internally and owner of a disjoint subset of tasks, following the key-partitioning model: many single-threaded units, each authoritative over its share of state. The natural partition key is `data.topic`—the same topic the task is announced on and that nodes are already subscribed to according to their specialty (§2.1)—so partitioning the Task Broker introduces no new concept: it groups under one process all the tasks that already share a topic anyway and compete with each other. A `task.announced` is routed to its partition by hashing on `data.topic` (consistent hashing, so that adding or removing partitions does not reshuffle the rest of the map), with no central coordinator on the critical path. Atomicity remains local (a partition never needs to coordinate with another to grant a task, because two tasks of different topics never compete with each other) and global throughput scales by adding partitions. This resolves the tension between "single-threaded" (§3.1) and "highly scalable" (Executive summary): "single-threaded" is correct at the partition level, and scalability comes from the number of partitions, not in spite of them. **How many partitions the Task Broker's ring has, and what moves when that number changes, is not its concern but that of the cross-cutting axis it shares with the other partitioned components** (§3.19): its assignment state lives in the State Registry precisely to satisfy the only requirement that axis imposes.

> **Namespace note:** the three states above are internal to the Task Broker and do not map one-to-one to the `type` of bus events (`task.*`, see §3.8), although some trigger the others. A `task.announced` event does not imply the `UNASSIGNED` state—the Task Broker re-announces the same `UNASSIGNED` task as many times as needed. They are two separate vocabularies that coexist over the same task.

### 3.2. The Tracing Collector: distributed observability and Trace Context
Asynchrony removes the linearity of the process. To recover traceability and debug the "black box", the system adopts the **OpenTelemetry (OTel)** standard—but **passively**, in the sense of §2.1: nobody reports telemetry to anybody, and no node exports its own to an APM backend.

* **Trace Context propagated, not exported:** Every user request generates a global, unique `TraceID` (§3.5). Each Bus event inherits that `TraceID` and a `SpanID`/`ParentSpanID` in W3C Trace Context format (`traceparent`, §3.8.1)—the responsibility of the Integration Sidecar (§3.6.1) when emitting the event, not an additional integration each node has to maintain. This is all any node does for traceability: propagate the context in the events it already emits anyway.
* **Tracing Collector (structural node, passive, §2.1):** a node broadly subscribed to the Bus (to any event carrying `traceparent`) reconstructs the span hierarchy from what it observes, without the rest of the network explicitly reporting anything to it or knowing it exists. Each observed `task.assigned` opens a span (the root, which is not assigned, opens it with the `task.announced` of its entry subtask, §3.5.1); each emitted `task.completed`/`task.failed` closes it; the `ParentSpanID` is derived from which `subject`/`traceparent` originated which. An observed `notice` (§3.8.2) **neither opens nor closes any**: it is not a unit of work but a point fact about the trace, so it is recorded as an annotation within it—a *span event* in OTel vocabulary—and its `subject` takes no part in deriving parentage. `task.proposed` and `task.rejected` (§3.8.2) get the same treatment: they carry `traceparent`, so the subscription predicate reaches them, but they open or close nothing—they are recorded as a *span event* of the span that `task.assigned` opens, without taking part in deriving parentage. With that, each task records not only who won the auction but against whom and with what proposal each candidate lost. Network-scope notices do not even arrive here: since they carry no `traceparent` (§3.8.1), they fall outside the subscription predicate of this very point. The Tracing Collector exports that reconstruction to a standard backend, where APM tools consume it without any integration specific to this architecture—but it also remains available for programmatic queries from other nodes (§3.10). **Exporting does not exempt it from retaining**: the aggregate by `TraceID` over which the enforcement of §3.15.2 runs is kept in the Tracing Collector itself regardless of the backend that receives the export, because that aggregate holds up a brake of the network and cannot hang on an external observability tool.
* **The Tracing Collector only sees what crosses the Bus (§2.2):** internal retries (§3.3) generate no event, so they generate no span—they are indistinguishable from a first-time success. The internal telemetry a node wants to keep for its own use (debugging, token counting per individual call) is its own private business.
* **Structural because of the half that is not here:** the Tracing Collector is structural (§2.1) not because of traceability—which does degrade without breaking anything—but because it builds the enforcement of the anti-abuse budget on the same aggregate by `TraceID` (§3.15.2). There it also opens a query to the operator and emits the terminal event of a trace's entry subtask, which the passive axis of §2.1 does not forbid. This section describes only the observational half; the containment half, and what happens when a Tracing Collector partition is missing, is defined in §3.15.
* **Why telemetry is not exported from each node:** it keeps the Integration Sidecar (§3.6.1) simple—it needs no OTel SDK or export client, only to stamp `traceparent`, which it already does—and it avoids coupling every node of the network to the chosen tracing backend. It is a single integration point (the Tracing Collector) instead of N.

### 3.3. Retries and escalation: a node decision, not a system protocol
The system runs no automatic retry or escalation protocol (§2.2), except reopening a subtask left outside the current vector space (below). When a node receives a `task.failed` or `task.rejected` on a task it emitted itself, deciding what to do is its own business. What the network offers is not a mechanism that fires on its own, but a common vocabulary so that, when a node decides to retry, that decision is legible and traceable by the rest of the network:

* **Retry levels:** a node can retry *internally*—self-correction, re-prompting, local validation—without generating any event on the Bus; from outside it is indistinguishable from a node that got it right the first time. Or it can retry *toward the network*, publishing a `task.announced`—the `cfp` of §3.8—that opens a new attempt at the subtask; this one is visible and stays in the OTel trace (§3.2).
* **Reopening without preference for the previous owner:** on reopening, the task competes again on equal terms—the Task Broker must not favor the node that held it before; selection follows the same similarity criterion as always (§3.7). The same node winning it again is an emergent result (better context already hydrated, better similarity), not an assignment the system guarantees.
* **Each attempt is a task of its own.** Reopening announces a new attempt, with its own `TaskID`, and `data.previous_attempt` names the attempt it reopens; the chain those pointers form is the subtask's **lineage**. A reopen is valid only on a subtask that the requester opened from the task assigned to it, whose terminal event it has already received—any of them, except the `task.completed` of a human query and the terminal event of its final round (§3.5.2)—and that is the last attempt of its lineage; and it keeps its topic. The requester's Integration Sidecar enforces this (§3.6.1). One `TaskID` per attempt is what leaves the rest of the network intact: the reopened attempt does not leave its terminal state (§3.1), the tie-break draw, seeded by `TaskID`, is drawn again (§3.7.5), effect deduplication by `TaskID` does not mistake the work that has to be redone for a duplicate (§3.6.4), and the new attempt writes in its own section of the Context Store and reads that of the previous one (§3.14.3).
* **Changing topic is not reopening.** A requester that takes the work to another specialty announces a new subtask, with a lineage that starts from zero. Needing another topic says the subtask was badly requested, not that the previous attempt solved it badly, so that attempt is not charged with any reopen (§3.12.2).
* **Regenerating vs. reusing the embedding on reopen:** if the reopen respecifies the task (e.g. adding a failure's traceback to the description), the embedding is regenerated; if only declarative metadata changes, it is reused (§3.7.4).
* **`current_attempts` as optional vocabulary, not as an automatic trigger:** this payload field (§3.8.1) lets a node signal, on reopening, how many times that subtask has already been attempted. What to do with that data is its own decision: correcting the prompt and respecifying, opening a new subtask on another specialty, or opening a `hitl_contact_*` subtask to ask for human help (§3.5.2) are equally valid options, never something the system imposes after a certain number of failures.
  * **There is no "cost" axis in this vocabulary.** A node does not declare, on reopening, that the problem exceeds the capacity of a cheap model, nor does it ask for a more expensive one, and the absence is not an omission: whoever reopens is the worst-informed actor for that prediction—it does not see inside any candidate (§2.2) and decides before anyone tries again; the award could not use the data without coupling itself to historical performance, which §3.13.4 explicitly forbids; and the network actively suppresses redundant coverage (§3.13.2, §3.13.4), so in the typical auction there are not two candidates of different cost to choose between. **Economic efficiency is not a routing problem but one of the node lifecycle** (§3.13), where the data needed—how much a node costs and how well it performs—does exist, aggregated over many attempts and not predicted over one.
* **What `current_attempts` counts and who consumes it:** it is neither a private counter of the node nor something accumulated at the level of the whole `TraceID`—it is a counter tied to the **reopen lineage of a specific subtask** (the requester↔subtask relation of §3.9.1), which travels in the payload of each attempt. The requester's Integration Sidecar stamps it—that of the reopened attempt plus one—and not the Logic Container that decides to reopen (§3.6.1): the number decides which channels enter each round (§3.5.2) and counts against the trace's budget (§3.15.1), so declaring it would mean skipping rounds or dodging the ceiling. This matters because, by design—reopening does not prefer the previous owner—the node that wins a reopen need not be the same one that lost before: if `current_attempts` were a private counter, a new node winning the task would have no way of knowing how many times it had already been attempted. Since it travels in the payload, any node that claims the task—whether it took part before or not—can read it.
  * **It is not exclusive to any role:** it applies to any requester that emitted a subtask and received `task.failed` on it—not only to the typical case of correcting after a failed verification (§5.2). A requester whose context-retrieval subtask returned nothing useful, or whose integration subtask ran into a merge conflict, is in the same situation and accumulates `current_attempts` on that subtask like any other.
  * **It does not require external verification:** `task.failed` is not reserved to a dedicated verifier node; any node that executed the task can evaluate itself and emit it by its own criterion (§3.9.2), with no third party auditing it. Attempt counting does not depend on a verification role existing in the network.
  * **Main consumer: the policy of the reopening node itself.** The intended use of this field is that the node about to decide whether to reopen again reads it before deciding—so its own criterion (defined by whoever created it) can choose to change approach or ask for human help instead of blindly reopening one more time. The Task Broker deliberately does not consume this field for its selection logic: doing so would couple it to task content and violate reopening without preference for the previous owner; its role stays simple and outside this decision.
* **Unfair reopening is bounded.** A reopen counts against the `reopen_rate` (§3.12.2) of whoever closed the reopened attempt, so a malicious requester can reopen good results to harm that node. The requester judging is the design (§3.9.2); what the network bounds is whom that judgment can target and how much it costs:
  * It only reaches nodes that worked for it, through the conditions under which a reopen happens (*each attempt is a task of its own*, above), and the Network Monitor counts the reopen only if the same requester publishes it (§3.12.2).
  * **The requester does not know who solved its subtask:** the terminal event reaches it without `source` (§3.6.1), and `trace_query` returns no node identities to it (§3.10). Knowing it, it would reopen only the results of the node it picked and make it lose the blue/green (§3.13.4); blind, its bias falls evenly over the niche, and an even bias does not decide the comparison between original and candidate.
  * Each reopen is one more attempt that enters its `cost_subtree` (§3.12.2) and the trace's budget (§3.15.1): the requester that distrusts without reason becomes the expensive node.

  A residual risk remains: a blueprint that marks its content so that an allied requester recognizes it, accepts it and reopens its competitors. It cannot be prevented without reading the content (§2.2); it is exposed in the reopens grouped by requester that `node_review` carries as evidence (§3.12.3), where the ally shows up as a requester that contradicts the others about the same nodes.
* **`failure_reason` as mandatory minimum context:** every `task.failed` (§3.8.1) includes a short, direct summary of the reason for the failure—the traceback of a broken test (§5.2), or the reason the Spawner gave about a badly specified vacant task (§3.13.2). It follows the same Claim-Check criterion as the rest of the system (§3.4): if the full diagnosis is heavy (extensive logs, history of several attempts), it is persisted in the Context Store under the `TraceID` and `failure_reason` carries the reference instead of the content. The requester deciding whether to reopen always has, at minimum, the short summary available without depending on an additional query.
* **`failure_code`: the reason the network classifies.** A `task.failed` whose cause the architecture fixes also carries `failure_code`, a value from a closed enumeration that the receiver recognizes without interpreting the summary. It is carried by the reasons that a network component—a structural component or the Integration Sidecar—establishes with a predicate over identifiers, and by those that a topic's contract closes, such as those of `hitl_contact_*` (§3.5.2). The section that defines each of those failures fixes its reason. A failure judged by a Logic Container carries only `failure_reason`, which is also mandatory alongside the code, because it is what a person reads.
* **The Integration Sidecar reopens the subtask left outside the vector space.** It is the only reopen the node does not decide. A `task.failed` with `failure_code` = `stale_vector_space` (§3.13.2) says nothing about the task: it says its `task_embedding` is from a model the network no longer uses, and the embedding is something the Logic Container does not see (§3.7.4). The requester's Integration Sidecar does not deliver it: it reopens the attempt with the same topic and the same payload, and the embedding comes from the current model (§3.6.1). For the Logic Container the subtask is still in progress, with the `TaskID` it received when announcing it. The reopen counts in `current_attempts` and in the trace's budget like any other (§3.15.1).
* **Network anti-abuse:** nothing in this core prevents a node from reopening a task indefinitely—containing that pathological case is a later layer over the network, not a piece of each node's decision model (that is why it lives separately, not here). The concrete mechanism—budget per `TraceID`, who enforces it and what happens when it triggers—is defined in §3.15.

### 3.4. The Context Store and efficient memory management (Message Bloat)
To guarantee low latency and avoid RAM saturation on the Event Bus, the system strictly implements the **Claim-Check pattern**:
* **Context Store:** Heavy context (entire repositories, massive error histories, testing logs) never travels in the event. It is an **off-Bus service** (§2.1) with a single, bounded responsibility: persist the context of a task in progress, categorized hierarchically under its `TraceID`, and serve it to any node of the network that needs to read it. It is a service and not a node in the sense of §2.2: it subscribes to no topic, does not compete by similarity and emits no events—each node's Integration Sidecar queries it on the node's behalf, off the Bus (see *Data Hydration*, below). Its place in the architecture is that of the Bus itself, a shared substrate whose availability the deployment guarantees, not a peer that takes part in the task market (§2.1, §3.14.1). It is the functional equivalent of the *Blackboard* of the base architectural pattern (§2): a shared place where nodes leave and pick up information without communicating with each other directly.
* **Internal storage mechanism (outside the contract):** *How* the Context Store stores and references that context (pure memory, tiering to disk, compression) is an internal implementation detail of the service, not an architectural decision of the system—the rest of the network only knows its contract (store by `TraceID`, serve by reference).
* **Retention and deletion (part of the contract):** unlike the storage mechanism, how long a piece of data lives and who can delete it is not left to the implementation, because the Context Store holds source code and user data, and that brings obligations the network must guarantee uniformly, whatever backend is chosen:
  * **Expiration on trace close:** the content of a `TraceID` is purged automatically when all the tasks of that tree have closed with their terminal event (`task.completed`, `task.failed` or `task.aborted`, §3.8.2), plus a grace window (`context_retention_grace`, a Global Configuration parameter, §2.3) that allows post-mortem debugging. It is not a fixed TTL per entry but is tied to the real lifecycle of the trace—a long trace must not expire halfway just because a fixed time has passed since the first write.
  * **Explicit on-demand deletion:** besides passive expiration, the Context Store exposes an immediate purge operation by `TraceID`, for when the user asks for their data to be deleted before the grace window expires on its own. It is authorized with the scope token of the trace root (§3.14.3), not with a new mechanism.
  * **Where the contract ends:** the internal mechanism that detects "trace close" and runs the purge (polling, the backend's native TTL, a cleanup job) is an implementation decision; the guarantee itself is not. The *value* of the window does not come in here: it is the operator's calibration over a declared key (§2.3), not a choice of the backend.
  * **Nothing survives the window, in any component.** The Context Store organizes its content by `TraceID`, never by user or by conversation, so once the grace window expires that content exists nowhere in the network—there is no backup copy and no component that retains it under another criterion. A conversation history that survives the close of its `TraceID`s lives on the person's side—in the client that shows it to them, or in the service where it takes place, like a mailbox thread or a chat history—with that side's lifecycle, and the channel puts it back into each trace as context for the request (§3.5.1). It is the same criterion by which the network delegates the identity of the person behind a channel instead of modeling it (§3.5.3).
* **Data Hydration:** Messages on the Bus are tiny and contain only references (keys/pointers). Before assembling the prompt or, in a deterministic node, before executing its logic, the Logic Container of the node that wins the task decides which portion of code or history it needs—a domain decision, exclusively its own (§3.6.1)—and asks its Integration Sidecar for it through the Node Runtime Interface, never crossing the Bus. It is the Integration Sidecar that performs the *hydration*: it downloads that portion from the *Context Store*, attaching the scope token it has held since it invoked the Logic Container (§3.14.3), and returns the result to it. The Logic Container never sees the token or talks to the Context Store—the Integration Sidecar is, here too, the node's only point of contact with the outside of its deployment unit (§3.6.1).

### 3.5. Human-system interaction: the User-Proxy (API Gateway / Human-in-the-Loop)

To preserve the integrity, security and synchrony of the swarm, **the human user never interacts directly with the internal Event Bus**. Communication with the outside goes through a boundary component called the **User-Proxy**, which acts as an **API Gateway** and a bidirectional intermediary (*Human-in-the-Loop Pattern*).

#### 3.5.1. Key responsibilities of the User-Proxy

1. **Generating the trace context (`TraceID`):**
   On receiving the user's initial request (via CLI, WebSockets, REST or an IDE extension), the User-Proxy generates the global, unique `TraceID`. It packages the original prompt, initializes the *Context Store* and publishes the triggering event—the `task.announced` of the entry subtask (below, §3.8)—on the Bus, always on `intake` (§2.1), the entry topic. It never decides a domain topic; that classification is left to the first semantic node that claims it. In that same act it stamps the current `config_version` in the envelope, which the whole trace inherits unchanged (§2.3): pinning the configuration is part of opening the trace, just like issuing the scope token (§3.14.3).

   > **Structural topics and affordances.** The Entry Node not choosing a *domain* topic does not mean `intake` is its only possible output: a channel can expose different entries, and it is the entry used—not the content of the message—that fixes the topic. That is what lets the Operator Channel emit on `config_change` (§3.14.4) without classifying anything, and what keeps the prohibition intact: the decision remains structural, never semantic. The same affordance admits entries whose sender is not a person but another Zobik network asking for an already classified artifact (§6): the request is announced directly on the topic that corresponds to it, without going through `intake` or any classification, because unlike a person stating an intention in natural language, the sender already knows what it is asking for. For the same reason, the request brings the announcement text and the material separately (§3.7.4): the channel announces the text as it arrives and leaves the material in the Context Store of the trace it opens, without composing either of them.

   **Opening a trace is a right granted by the deployment or the operator, never by the network.** Opening it fixes the configuration it is judged under, opens a budget (§3.15) and gives purge scope over it (§3.14.3). The Entry Node and the Operator Channel open it with the credential provisioned with the deployment (§3.14.2). An emergent channel opens it only if the `node_provision` that brought it up grants it an entry topic (§3.13.8), and the root announcement always goes on that topic: its Logic Container does not choose it. In that channel the Integration Sidecar carries out the act (§3.6.1). Whoever opens the trace chooses the root's `workspace` (§2.4), because it is the one that knows which project the request is about. Opening it also fixes whom `requester` reaches throughout the trace: the audience of the channel that opens it, which the trace inherits as `origin_audience` (§3.5.3).

   **The trace root is a task of the channel that opens it, and that channel closes it.** The `TraceID` is the `TaskID` of that root, which does not go through an auction: the channel holds it as assigned from the moment it opens the trace, and the request travels in a subtask of the root, the **entry subtask**, with its own `TaskID` and on the entry topic. Whoever resolves the entry subtask closes it like any other, addressed to the channel, which is its requester (§3.9.1); the channel delivers that outcome to whoever originated the trace and only then closes the root (§3.5.4). What the channel does on the trace outside the delivery—an acknowledgment, a progress notice—it does on the root, and its cost travels in the terminal event that closes it (§3.10).

   **The entry subtask separates the request from its context.** The request is the message the trace comes from: its text is that of the announcement, from which the `task_embedding` comes (§3.7.4), and its attachments go to the Context Store as request material. The context is what the person has in view alongside that message—the earlier messages of their conversation and their attachments—and it goes to the Context Store as context material, referenced separately from the request. The channel puts into the trace the context the person sees, without choosing or summarizing any of it: what to use belongs to the node working on the subtask, and a request that relies on what came before is interpreted by the first semantic node that claims it, by hydrating the context. A channel with no context to offer opens the trace with the request alone, and each message it receives starts a new conversation. Between one trace and the next, the person's side keeps the conversation (§3.4).

2. **Input sanitization:**
   It applies security filters to prevent *Prompt Injection* attacks before requests reach the workers, and normalizes the *shape* of the payload (encoding, size limits), never its semantic content. The prompt is preserved intact and in the language the user wrote it in: translating it would be a semantic decision, and the User-Proxy is deterministic (§3.6.3) for the same reason it does not choose a domain topic. Preserving the original is also what keeps the trace auditable and what lets the `hitl_contact_*` cycle (§3.5.2) speak to that person again in their language with no loss accumulated over round trips. If some internal language ends up prevailing as a lingua franca, it emerges from how the blueprints are written, not from a policy at the edge.

   > **Different from topic names:** a topic (§2.1) is a namespace identifier, not natural language. Minting them as stable ASCII slugs (`code_review`) is a naming convention needed for matching between nodes to work, and it does not contradict the above: the user's content is not translated; channels are named.

3. **Human-in-the-Loop orchestration:**
   The User-Proxy is the node that carries out contact with the human, but it does not do so by intercepting any privileged Bus event: it serves tasks on the `hitl_contact_<audience>` topic that corresponds to it just as any other node serves its topic, through the usual CNP cycle (§3.5.2). It presents the query as it arrived in that person's interface and returns the answer as the result of that task, without reinterpreting either (sanitization normalizes the shape of the payload, never its semantic content): the work of phrasing the question in terms that audience understands belongs to the semantic node that opened the subtask, not to the edge that delivers it. Each instance serves one audience, not "the human" in general (§3.5.3).

4. **Interface decoupling (client-agnostic):**
   It isolates the internal infrastructure (VPC/private network) from the end client. The swarm of nodes and the Bus remain intact regardless of whether the user's interface is a command console (CLI), a web dashboard, a Slack bot or an extension inside the code editor (VSCode/JetBrains). Each channel is a distinct instance of the User-Proxy role (§2.1), and that multiplicity is what makes the multi-channel escalation of §3.5.2 emerge with no dedicated policy. An emergent channel receives messages from outside through its ingress (§3.16.7).

#### 3.5.2. `hitl_contact_*`: asking for a human decision is emitting a subtask

Every pause for human intervention in this network—without exception—is expressed in a single way: the node that needs the decision becomes the *requester* (§3.9.1) of a subtask of its own on a topic of the `hitl_contact_<audience>` family (§3.5.3). There is no event `type` dedicated to "asking for a human" or to "the human answered": the circuit reuses the entire CNP lifecycle (§3.8, §3.8.2).

A node blocked waiting for a human is, then, a node waiting for the result of a subtask it emitted—exactly the case of §3.9.1. There is no lease in limbo, no "paused" state the Task Broker has to understand, and no ambiguity about whether that wait counts toward `current_attempts` (§3.3). The `task.completed` of that subtask reaches the requester, which is precisely the one that was waiting, and any instance of the User-Proxy role that serves that audience takes the subtask, with no privileged subscriber. Everything that follows—timeout, reopen, escalation—comes from the vocabulary that already exists.

The full cycle:

* **Round 1—deterministic routing, but only on the trace's origin audience:** when the query goes on `hitl_contact_<origin_audience>` (§3.5.3), the channel that owns the `TraceID` is the obvious first contact—it is the channel that opened the trace, and the one the originator is using. Since no admission criterion of this family models "who has the active session" (§3.7.5, step 4), the same deterministic routing that `trace_query` already uses applies (§3.10): the owner selects itself because it recognizes that `TraceID` among the roots it holds (§3.6.1), and the other channels of the audience abstain in that round. Both sides decide it with fields the announcement already carries: the topic, `origin_audience` and `current_attempts`. **This exception does not generalize:** on any other audience the normal auction governs from the first round, and the owner of the `TraceID` is not eligible at all—the topic it claims is that of its audience, and no node claims two (§2.1). Reaching that same person through another audience, if the channel does reach them, is the work of another node, which competes there like any other (§3.5.3).

  If that owner **is no longer there**—session closed, process down—it does not propose and the round goes vacant (§3.7.5, step 5). The Spawner closes it with `task.failed` on that first vacancy (§3.13.2), the requester treats it as a round without an answer (below), and its reopen opens round 2 to the rest of the audience. No prior liveness check is needed, and the cost of that absence is an auction timeout, not a `hitl_response_window`—the window only starts running when someone actually took the task and the human did not answer.
* **Timeout without an answer → normal reopen:** if the human does not answer within `hitl_response_window` (§2.3), the User-Proxy that held the task publishes `task.failed` with `failure_code` = `unanswered`, or `undelivered` if within the window it did not manage to get the query to them (the same contract as any other node, §3.3). A channel that stops reaching the person before the window expires—a session that closes—closes the task at that moment, with the same `failure_code`. The requester reopens it, and the new attempt carries an incremented `current_attempts` (§3.3)—from here on, any other User-Proxy instance **of the same audience** (e.g. a WhatsApp or email channel, if one exists) can propose, with no special routing and without competing by similarity: on this family admission is by credential and audience membership, and the topic already determines it (§3.7.5, step 4).
* **Each channel declares in which rounds of the lineage it is a candidate: its `attempt_window`.** A round is an attempt of the lineage (§3.3): the Task Broker's re-announcement of the same attempt (§3.1) does not advance it, because it does not change which channels are eligible, and that is why a vacant round is closed on its first vacancy (§3.13.2). The window is a range over the `current_attempts` that already travels in the payload of each reopen `task.announced` (§3.3)—the field exists precisely so that a node that did not take part before knows where in the lineage it stands. The same local filter of §3.7.5 (step 3) evaluates it, going from "is this within my competence?" to "is it my turn?": self-selection, not ranking, and no new state anywhere. The lower bound lets a channel abstain *before* its round; the upper one lets it stop proposing after it. The window also declares whether the channel competes in the final round (below). Without a declaration, the channel competes in every round, including the one that follows its own failure and the final one.
* **"Without repeating the original" needs no systemic exclusion:** the channel that failed stops being a candidate because the lineage moved past the upper bound of its `attempt_window`. No "who already tried it" bookkeeping is needed—it would be the kind of rigid state the architecture avoids elsewhere (§3.13.5).
* **Multi-channel escalation emerges for free, and never crosses audiences:** if there are several User-Proxy instances tied to different channels (chat, WhatsApp, email—all equally valid as the User-Proxy role, §2.1), the sequence of reopen rounds already builds the escalation without needing a separately configured policy—it is the same reopen with which any requester retries a subtask (§3.3). Since the reopen always happens on the same topic, escalating from chat to email within an audience works, and escalating *toward another audience* is structurally impossible: no additional rule is needed to forbid it (§3.5.3).
* **The *order* of that escalation comes from the `attempt_window` values, not from a configured policy.** What is wanted in practice is to go from the cheapest and least invasive to the most intrusive—chat, then email, then SMS or pager—and the abstention by window already produces that, with no coordination: each channel declares its window in its own blueprint and the order emerges from those declarations. **It deliberately does not live in Global Configuration** (§2.3): a centrally declared order would have to name concrete channels—emergent nodes the Spawner creates and archives—it would be the only entry of that configuration that references node identities instead of audiences or scalars, and it would make adding or removing a channel depend on a second edit, besides the request with which the operator brings it up or takes it down (§3.13.8). With the window in the blueprint, adding or removing a channel touches nothing but that channel.

  The failure mode is the cheap one: if, through poor authoring, no channel declares itself for round 1, that round goes vacant and costs an auction timeout, not a `hitl_response_window`. And if several share a round they are peers by definition (§3.5.3), so the Task Broker's atomic award decides among them with no need for any additional criterion.
* **The last round is the final one, and it belongs to the channel that can wait for the person.** The ordinary rounds end when one after round 1 goes vacant, because no channel of the audience is enabled in it (§3.13.2). The requester then reopens once more, and that attempt carries `final_round`, stamped by whoever stamps `current_attempts` (§3.3). Only the channels whose `attempt_window` includes the final round compete in it, whatever their range, and its terminal event is not reopened: a query exhausts its rounds when the final one closes without an answer. That way a channel the person opens when they come back can go first and last—in round 1 if it reaches them at that moment, and in the final round to hold what no other channel delivered—without its window depending on how many channels the audience has. With no channel enabled, the final round goes vacant and costs an auction timeout.
* **Closing:** the User-Proxy that gets an answer publishes `task.completed` on the subtask, with the human's decision referenced via Claim-Check (§3.4). The concrete *disposition*—approve, reject, continue, accept partial, abandon—travels in the payload, never in the `type`: it is the content of an answer, not a variant of the protocol. A `task.failed` on a `hitl_contact_*` topic means exactly one thing, and only one: no human answer was obtained. Its `failure_code` (§3.3) says why, with one of these values: `undelivered`—the query did not reach the person: no channel claimed it and the Spawner closed it (§3.13.2), or the channel that took it did not manage to deliver it—or `unanswered`—it arrived and nobody answered within `hitl_response_window`. A query treats both the same: as a round without an answer, which the requester reopens or, once the final round has closed, resolves with its conservative way out. The delivery of a trace's outcome tells them apart (§3.5.4). **On this family only a `task.failed` is reopened.** Reopening an answered query would escalate toward more intrusive channels against a person who already answered, and would charge a reopen to the channel that brought the answer (§3.12.2). If the answer is not enough, the requester opens a new query, which starts at round 1.

**When the requester is structural, the exchange is a contract.** Closing leaves the disposition in the payload and does not fix its shape, and for an emergent node that is right: the network does not look inside a node (§2.2). But when the one asking is a structural component, **the shape is not left to any implementation**: a network component builds it and any channel of the audience renders it, without knowing the condition that originated it. A single invariant then governs, which each case instantiates with its own table:

* **What goes** in the `data` of the `task.announced`: `kind`, `scope` (`trace` | `network` | `niche` | `audience` | `egress` | `call`), `since`, `options`—a closed enumeration of admissible answers—and `outcome_if_silent`, the element of `options` that the requester applies if nobody answers. The latter does not repeat the network policy: it is what lets the question be answered without knowing that policy—whoever decides sees what happens if they do not decide.
* **What comes back**: `data.decision`, exactly one of the values of `options`. The delivery of the outcome is the exception: without `options` it comes back without `decision`, and a `reject` also brings its reason (§3.5.4).
* **What does not fit is treated as silence.** An answer with a `decision` outside the enumeration is not a decision the requester has to interpret: it treats it as an absence of human decision and applies `outcome_if_silent`. It is the same rule that governs the timeout, applied to the other way of getting no answer, and it closes the only door through which a malformed payload could authorize something.
* **And an `evidence` block: the observed facts that support the condition, raw and enumerable, never prose.** It follows the same criterion by which the Tracing Collector emits a closed enumeration over raw data (§3.6.3) and by which any deterministic node emits a `failure_reason` without interpreting it, leaving the reading to whoever receives the event (§3.6.3, §3.3). It is what separates "pick one of three" from "pick one of three with judgment", while producing the announcement stays deterministic. The identifiers that travel there—`TaskID`, `topic`, `node_id`, `TraceID`—are also the ones that enable a second query (§3.10, §3.12.3) without the producer having to anticipate it: that is why the narrative reconstruction remains optional and *pull*-based (§3.15.4) instead of a fixed cost of every notice.

The current instances are `budget_exceeded` (§3.15.6), the network-scope ones of §3.15.7, the egress ones—`egress_unavailable` (§3.16.5) and `gate_approval` (§3.16.4)—and `result_delivery` (§3.5.4). **The egress gate belongs here even though an emergent node triggers it, because of who builds the payload and not who publishes it:** the Integration Sidecar produces it, and it is deployed infrastructure, identical in every node (§3.6.1), so its fields are fixed like those of any other instance without the network having to understand what the task does.

**Different origins, a single circuit.** What varies among the origins is who decides to open the query, and which audience it goes to depends on that:

* **An emergent node, by its own criterion, only to `requester`**—to clarify an ambiguous request, or so that whoever originated it validates a plan or a result before going on (§3.9.2). `requester` resolves in every trace of every network (§3.5.3), so a blueprint that queries it works equally in any network that hosts it (§3.13.6); and clarifying a request is part of working on it. The Logic Container asks for it through a dedicated request of the Node Runtime Interface, which names no audience, and the Integration Sidecar rejects any other announcement from it on the family (§3.6.1).
* **The egress gate, to the audience the rule names**—mandatory by contract (§3.16): it is triggered by an exit from the substrate whose rule ends in an audience, be it `requester`, `operator` or another (§3.16.2). Neither the obligation nor the audience is the node's decision: both come from Global Configuration (§2.3), and the one that opens the query is its Integration Sidecar.
* **A structural component, to `operator`**—the producer of a condition only the operator decides: the Tracing Collector on a trace (§3.15.2), the Network Monitor or the Spawner on the network (§3.15.7), and the Spawner on a niche or an egress interface (§3.13.2, §3.13.5, §3.16.5). It does not choose the audience: what the network cannot decide alone belongs to the operator (§3.17.1).
* **The channel that opened the trace, to the origin audience, to deliver its outcome**—mandatory by contract (§3.5.4): its Integration Sidecar opens it on receiving the terminal event of the entry subtask, and the audience is the trace's `origin_audience`.

**No other path opens a query.** A node that needs another person's judgment asks for it as work, on a topic served by a human-backed node (§3.6.3), and accepts that result by its own criterion like any other (§3.9.2). The operator declares a process rule—who approves what—over the effect it protects (§3.16.2).

#### 3.5.3. Audiences: the network distinguishes human populations, not people

A single network may have to contact different humans, with different authority, through different channels—the example of §5.4 has them all at once: the customer who opened the ticket, whoever approves a refund, and whoever resolves the escalation. Confusing them is not an imprecision: if the operator assigned refund approval to finance, asking the customer who requested the refund to approve it is exactly the failure the egress gate (§3.16) exists to prevent.

**The audience is a property of the topic, not of the human.** `hitl_contact` is not a topic but a family: `hitl_contact_operator` (whoever operates the network), `hitl_contact_user` (whoever asks it for work through the deployment's entry, §2.1), one `hitl_contact_<audience>` for each population that the `egress_registry` names in the outcome of some rule (§3.16.2), like `hitl_contact_finance_approval` in the example of §5.4, and one for each population reached by an entry channel the operator brings up (§3.13.8), like the `hitl_contact_customer` of the same example. There is no other: `hitl_contact_operator` and `hitl_contact_user` exist in every network, the operator creates the rest, and no node mints an audience. Each User-Proxy instance serves **a single** audience—the one its channel actually reaches—and competes only for that audience's topic, which is the only one it claims (§2.1). A channel that reaches two populations is two nodes, not one. Every channel other than the two the deployment brings up is brought up by the operator (§3.13.8), who can bring it up before a rule names its audience: until then it receives no queries.

**`requester` names the trace's origin audience.** Every trace is opened by a channel, and it inherits that channel's audience as `origin_audience` (§3.5.1, §3.8.1). The Integration Sidecar resolves `requester` to `hitl_contact_<origin_audience>`, both in the query the Logic Container asks it for and in the gate whose rule ends in `requester` (§3.6.1, §3.16.4): the one asking does not know the network's entries, and the query reaches the channels that reach the population of whoever originated the trace, and no other. It is a reference resolved per trace, and that is why no audience is called `requester`.

* **The audience is the topic, never a payload field.** The Task Broker's partitioning is by `topic` (§3.1), so as topics, audiences already have routing, vacancy and governance (§3.7.6) solved, without adding any `type` (§3.8) and without the Task Broker having to read `data` to route—the same coupling §3.16 avoids.
* **The network names audiences and channels, never people.** There is no user registry, no ACLs and no model of human roles on the Bus. Which concrete person is reached within a channel, and whether they are authorized to decide what they are asked, lives inside the User-Proxy's blueprint and its external system (IdP, Slack group, CRM)—§2.2, and the same criterion by which §3.14.1 delegates node identity to the deployment platform. The network defines no human-identity mechanism because it does not need one: it is enough that a channel serves one audience and not another.
* **Different from a human-backed node (§3.6.3):** a topic like `support_escalation` (§5.4) is work a human *performs*, and its node competes for it like any worker. A `hitl_contact_<audience>` is a query a human *answers* about another node's task. That in both cases there is a person on the other side does not make them the same pattern.
* **Audience topics do not go through topic governance.** Since no node mints them, they do not enter the Topic Registry or the neighborhood check (§3.7.6, §3.7.7), and two audiences do not collapse even if their queries look alike.

#### 3.5.4. Delivering the outcome

**A trace's outcome reaches whoever originated it through a subtask of the origin audience.** When the channel that opened the trace receives the terminal event of the entry subtask (§3.5.1)—a `task.completed`, a `task.failed` it does not reopen, or the Tracing Collector's `task.aborted` (§3.15.6)—its Integration Sidecar opens from the root a subtask on `hitl_contact_<origin_audience>` with that outcome. Round 1 of the origin audience falls to the channel itself, as owner of the `TraceID`, and if it does not deliver it, the following rounds go to the other channels of the audience (§3.5.2). That way the outcome arrives through another channel when the one that opened the trace cannot deliver it, and delivering it is an assigned task, whose cost travels in its terminal event like that of any other (§3.10).

**The Integration Sidecar opens it, so it instantiates the contract of §3.5.2:**

| Field | Value |
| :--- | :--- |
| `kind` | `result_delivery` |
| `scope` | `trace` |
| `options` | those that `result_delivery` fixes for the audience (§2.3): none with `none`, `received` with `ack`, and `accept` \| `reject` with `acceptance` |
| `outcome_if_silent` | `received` with `ack` and `accept` with `acceptance`; without `options` there is no silence to resolve |
| Decision data | the terminal event of the entry subtask: its type, its `failure_reason`, its `failure_code` or its `disposition` when it carries them, and its result by Claim-Check (§3.4) |
| `evidence` | the `TraceID`, the `TaskID` of the entry subtask and the trace's accumulated `cost` (§3.15.1) |

**The channel that takes it delivers it however its service allows:** over the connection that brought the request, if it is still open, or through egress (§3.16.7). Without `options` it closes it with `task.completed` on delivering it, without `decision`; with `options`, when the person answers. In both cases `hitl_response_window` bounds the round, and once it expires, the channel closes it `unanswered` if it delivered the outcome and `undelivered` if not (§3.5.2).

**It is reopened only with `undelivered`.** With `unanswered` the outcome has already arrived, and the Integration Sidecar applies `outcome_if_silent` instead of reopening: a person who read the answer and did not reply does not receive it again through every channel of their audience. When the ordinary rounds end, the delivery moves to the final round (§3.5.2), which is not reopened with any value. The delivery of a channel that competes in every round and never manages to deliver is reopened up to the trace's reopen ceiling (§3.15.1).

**A `reject` reopens the entry subtask.** Along with the `decision`, the answer brings a `failure_reason`—and a `failure_code` when the one rejecting is a network component that classifies the reason, like the Spawner facing a delivery from the Forge (§6.4)—which the Integration Sidecar puts on the new attempt (§3.3): the rejection falls on whoever closed the reopened attempt (§3.12.2), and the terminal event of the new attempt opens another delivery. It is the way whoever originated the trace rejects a result without opening another trace.

**Once the delivery is closed, the channel closes the root** with the terminal event of `subject = TraceID` (§3.9.1): `task.completed` if the outcome arrived—the delivery closed with `task.completed`, or with `unanswered` and its `outcome_if_silent`—and `task.failed` with `undelivered` if the rounds ran out without delivering it, the final one included. It is addressed to the channel itself, which is the root's requester, and it carries in `metrics` the cost of what the channel did on it (§3.5.1, §3.10).

**A frozen trace does not award the delivery**, which waits like any task until the trace is unfrozen or aborted (§3.15.3, §3.15.6).

### 3.6. Communication interface: the Integration Sidecar pattern and event emission

In a **Compound AI System** optimized for cost and latency, a fundamental architectural rule governs: *"Never use an LLM to solve a problem that can be solved with deterministic logic (traditional code)"*. 

Under this principle, **language models (LLMs) never interact directly with the Event Bus**. Integration happens through a structural design pattern, which categorizes nodes by their nature.

#### 3.6.1. The Integration Sidecar pattern

A node's container is split into two processes because two things of opposite nature live inside it. Integration with the Bus is identical for every node of the network and does not depend on the domain; the logic, on the other hand, ranges from a single LLM call to a full state graph, with phases, its own tools and internal retries, or a deterministic script. The boundary between the two processes is the one that separates the generic from the domain-specific, and the thin from the arbitrarily complex.

Every node is deployed as a single unit (same pod/deployment unit, same lifecycle—never one without the other) made of two processes:

* **Integration Sidecar:** a generic process, identical for any node of the network regardless of its nature (semantic or deterministic, §3.6.2/§3.6.3) or the complexity of its internal logic. It is solely responsible for:
  1. Keeping the connection with the Bus alive.
  2. Stamping on every event it emits what the trace inherits—`traceparent`, `config_version`, `workspace` and `origin_audience` (§3.8.1)—copied from the task it acts on. The Logic Container does not write it.
  3. Guaranteeing delivery of the event and avoiding processing it twice (§3.6.4)—deduplicating on reception, before forwarding the event to the Logic Container.
  4. Attaching the capability credential signed by the Spawner (§3.14.2) to every `task.proposed` the node publishes.
  5. **Deciding whether the node proposes** (§3.7.5, step 3): computing the similarity between the signed embedding of that same credential and the announcement's `task_embedding`, checking it against the `similarity_floor` the credential carries (§3.13.3), and checking the announcement's `current_attempts` and `final_round` against the `attempt_window` the credential also carries, together with the round 1 that the origin audience reserves for the owner of the `TraceID` (§3.5.2). If the announcement passes and the node is free, it publishes the `task.proposed` without consulting the Logic Container, which does not receive the announcements of its topic. A draining channel proposes only in round 1 of the traces it opened (§3.13.8).
  6. **Generating the `task_embedding`** of every `task.announced` the node publishes (§3.7.4), reading the **current** `embedding_model` from Global Configuration (§2.3), reaching the Embedding Model through the egress entry that value names (§3.16.3) and stamping in the payload the `model_id` derived from it (§3.7.3, §3.8.1).
  7. **Mediating access to the Context Store** (§3.4) on behalf of the Logic Container: it holds the scope token it received with each `task.assigned` and that of each trace it opened (§3.14.3), attaches to each read/write request the Logic Container passes it through the Node Runtime Interface the token of the task the request names, and returns the response as is—without interpreting what portion of code or history was requested or what was written. The Logic Container never talks to the Context Store or sees the token.
  8. **Mediating all egress** (§3.16) on behalf of the Logic Container: it resolves the slot the call names to its `egress_registry` entry (§2.3), builds the request from the fields and the body, executes it if appropriate and returns the response as is—without interpreting what was requested or what came back, except for the billing data it extracts through the entry's `billing_rule`. From that data and the current rate it composes `metrics` (§3.10). The Logic Container never sees the credential or reaches the destination by any other path.
  9. **Silencing self-selection while the node has a task in progress**—the capacity rule below.
  10. **Fixing the recipient and the task of every addressed event** (§3.7.4): the terminal event with which the node closes travels to the requester the task declares, and on that task's identifier, and it takes both from the `task.assigned` it holds for it (§3.8.1). The Logic Container decides which event to emit and on which of its tasks; whom it reaches, it does not, and it cannot name a task it was not assigned.
  11. **Closing the tasks in progress if its Logic Container goes down**: if the Node Runtime Interface session drops with assigned tasks, it publishes on each one a `task.failed` with `failure_code` = `logic_container_lost` (§3.3), stops renewing its lease and the node is left free, without proposing until the Logic Container reconnects: a node with no logic connected does not compete. A Logic Container that reconnects starts with no tasks: the state it carried inside is not recovered. The lease (§3.1) covers the failure of the whole deployment unit, where no process is left to publish.
  12. **Publishing on the `hitl_contact_*` family only through the paths that fix it** (§3.5.2): on the task's `hitl_contact_<origin_audience>`, the query to `requester` that the Logic Container asks it for through the request the interface reserves for that (§3.5.3); on the `hitl_contact_<origin_audience>` of a root it opened, the delivery of its outcome, which it opens itself (§3.5.4); on any other audience, the egress gate it opens itself (§3.16.4). It rejects an announcement from the Logic Container on a topic of the family.
  13. **Keeping the lineage of the subtasks the node opens** (§3.3): it holds the subtasks it announced from each assigned task and the terminal event of each one, and on a reopen it stamps `previous_attempt` and `current_attempts`—and `final_round` on the query whose ordinary rounds ended (§3.5.2)—and rejects one that does not meet the conditions of §3.3. The Logic Container decides which attempt it reopens; it does not write the link or the number. The exception is a `task.failed` with `stale_vector_space`: it does not deliver it, it reopens the attempt itself, and it keeps naming the subtask to the Logic Container by the `TaskID` it returned when the subtask was announced (§3.3).
  14. **Opening a trace when the node's credential grants it** (§3.5.1): only if the proof the credential embeds carries an entry topic (§3.13.8), and only from a message it admitted through its ingress and that no other trace used (§3.16.7). It generates the `TraceID`, writes into the Context Store the payload the Logic Container passes it and the message's bodies (§3.16.7), mints the root's scope token (§3.14.3) and publishes the `task.announced` of the entry subtask on the entry topic, with the current `config_version`, the `workspace` the Logic Container chose and its credential's `audience` as `origin_audience`, in a single act. It holds each root it opened as a task assigned to the node until it closes it, and afterwards until `context_retention_grace` expires (§3.4), even across a restart: with it, it recognizes the queries of its audience that it owns (§3.5.2), receives the terminal event of the entry subtask, opens the delivery of the outcome and closes the root (§3.5.4), and serves the egress calls and the purge the Logic Container requests on it. While draining it opens no traces (§3.13.8).
  15. **Mediating a channel's ingress** (§3.16.7): listening on each entry its `ingress_grants` associate or, if the entry names a `source`, holding the connection with it; admitting each message, handing the fields to the Logic Container with the bodies in the message area, taking those bodies to the Context Store in the act that resolves the message, and returning over the same connection the response the Logic Container asks it for. The Logic Container never sees the protocol request, or what the sender was verified with or the `source` was entered with.

  None of these responsibilities requires knowing what is inside the Logic Container (LLM, state graph, script)—the Integration Sidecar is, by design, blind to its content. Extracting a billing datum does not break that either: the rule says where to look in the response, not what the surrounding content means.

**Addressing the terminal event from the assignment is what backs the closing rule of §3.9.1.** A parent accepts as the result of its subtask what arrives addressed to it, and has nothing to check it against: it does not observe the award of the tasks it opens, so it does not know who was going to resolve them. With the recipient and the task written by the generic half of the node, a Logic Container cannot address a terminal event to a node that assigned it nothing, or answer a task it was not assigned. It is a guarantee of the same class as the confinement, and it rests on it: it holds because the Logic Container reaches the Bus through no channel of its own, so a deployment that does not provide that clause (§3.14.1) does not provide this one either. The rule governs the node that resolves the task it was assigned; a terminal event emitted without an assignment—the Spawner's `task.failed` on a vacant task, the Tracing Collector's `task.aborted` (§3.8.2)—is addressed by the requester the announcement declares.

**A node works one task at a time, and the Integration Sidecar enforces it.** The network assumes nothing else about a node's capacity: the `task.assigned` that grants it a task makes it busy, and from that moment **it publishes no `task.proposed` until it emits the terminal event of that task** (`task.completed` or `task.failed`, §3.8.2). It is the responsibility of silencing self-selection, in the list above, and it costs nothing extra: the Integration Sidecar is already the one that receives the `task.assigned`, decides whether the node proposes and publishes the terminal event, so the state it needs is the one it already has at hand. There is no new event, no new field, and the Task Broker does not find out.

* **Why the assumption has to be this one and not another.** The alternative—a node with its own concurrency—would force the network to know that capacity in order to tell whether a proposal is honest, and that is exactly what §2.2 forbids it to look at. One job per node is the only assumption that does not require the network to see inside. The Logic Container parallelizing internally to solve *its* task remains free (§2.2); what the network fixes is how many of its tasks there are at once, which is one.
* **It is behavior at the node's edge, not an award rule.** The Task Broker still arbitrates only by similarity (§3.7.5, step 4) and checks nobody's availability: a busy node simply does not show up in the auction. For §3.7.5 (step 3), a busy node falls on the side of **"no one decided to compete"**, just like one that does not reach the floor.
* **A node waiting for subtasks is still busy.** The closing rule of §3.9.1 leaves it waiting for its children until it can emit its own terminal event, and during all that time it does not propose. That is correct—the task is still its own and it has not finished it—and it has a consequence worth seeing: a niche served by a single node whose work opens subtasks on its own topic is blocked against itself. No rule is needed to get out of there; the subtask goes vacant, which is the case of the network's capacity (below).
* **The network's capacity comes from here**, and it is what lets a task go vacant while having coverage: if all the nodes of a niche are busy, nobody proposes and the vacancy fires just as if the niche did not exist. Resolving that ambiguity—waiting or bringing in another node—belongs to the Spawner (§3.13.2), and the criterion it resolves it by belongs to §6.
* **A `hitl_contact_*` channel is not governed by this rule: it holds all the queries of its audience that fall to it, and answers them one at a time.** The rule exists for nodes that execute work: it keeps one from hoarding its niche and becoming a bottleneck when others could resolve the work, and it lets saturation show up as vacancy so that the Spawner brings in another node. In a channel none of that applies: its capacity is the person's attention, and the Spawner does not instantiate channels (§3.13.2). Its Integration Sidecar proposes on every query its `attempt_window` admits, whether or not it has others pending, and the Logic Container names on each close the query it closes. That is why a vacancy on the family means that no live channel of the audience is eligible in that round.

**Generating the `task_embedding` is the only model call the Integration Sidecar originates on its own**—it executes the others on behalf of the Logic Container that asked for them (§3.16). It still meets the criterion: embedding a task's text is identical for every node, does not depend on the domain and requires reading nothing the Logic Container decided—it receives an already built event and adds a derived field to it. Putting it on the other side of the boundary would break several things at once: a deterministic node (§3.6.3) would stop having **zero token cost**, the Entry Node—which is deterministic and publishes the founding `task.announced` (§3.5.1)—would come to need a model client its contract does not contemplate, and each blueprint would carry a dependency that is not its own. For the same reason, **this call does not enter `metrics`**: that aggregate measures what it cost to solve the task the network awarded, and the embedding is not domain work but integration.

From this follows a property that §3.13.7 relies on entirely: since the Integration Sidecar is a generic process **deployed by whoever operates the substrate and not per blueprint** (§3.13.3), it reads the current parameter in its own cycle, without subscribing to anything (§2.3).

* **Logic Container:** the specialty of the blueprint itself. It can be as simple as a single LLM call or as complex as a state graph with phases, its own tools and internal retries (§2.2 imposes no shape); for a deterministic node (§3.6.3), it is simply the business script. It is responsible for:
  1. All internal reasoning/orchestration, whatever its shape—exclusively its own business (§2.2).
  2. Context hydration: it decides which portion of the Context Store it needs—a domain decision, exclusively its own—and asks its Integration Sidecar for it through the Node Runtime Interface; it is the Integration Sidecar that obtains it on its behalf, attaching the scope token it has held since it invoked it (§3.14.3). The Logic Container never talks to the Context Store or handles the token—the connection with the Store, unlike what to hydrate, is not its decision.
  3. Deciding which external calls its logic makes—to which model, to which API, how many times, with what retries of its own: a domain decision, exclusively its own (§2.2)—and asking its Integration Sidecar for them through the Node Runtime Interface, which executes them on its behalf within what the node has been granted (§3.16). As with hydration: *what* to call is its own; reaching the destination is not.
  4. Deciding which subtasks it announces, when it queries whoever originated the trace (§3.5.2) and how it closes its task—`task.completed` or `task.failed`—and asking the Integration Sidecar for it, which builds the event and publishes it. These are the only events it asks for, always on a task assigned to it, and it never publishes directly to the Bus. A channel with an entry topic also decides whether a message it admitted opens a trace, and when to purge one it opened (§3.5.1, §3.4, §3.16.7).

* **Local contract between the two—the Node Runtime Interface:** a fixed, minimal boundary, internal to the deployment unit (it never crosses the Bus and is not a new `type` of §3.8). The Integration Sidecar hands the Logic Container, already deduplicated, the `task.assigned` that gives it its task, the terminal events addressed to the node—without their `source`, because the requester does not know who resolved its subtask (§3.3)—and the `notice` events of the broadcast topics the node watches, and in a channel with ingress, the messages it admitted through its entries (§3.16.7); the announcements of its topic stay in the Integration Sidecar, which is the one that decides to propose. The Logic Container asks it to publish the events of its task: announcing subtasks or reopening them, querying whoever originated the trace, and closing it. In a channel with ingress it also asks it to answer a received message, over the connection that brought it, and on closing a query it names the message that answers it. The query is a dedicated request and not an announcement with a topic, so the Logic Container has no way to name another audience. Opening a trace is also a dedicated request with no topic, because the topic comes from the proof (§3.13.8). The same interface covers, in the other direction, everything the Logic Container needs from outside: reading or writing a portion of the Context Store, and going out of the substrate. In both, the Integration Sidecar operates on its behalf and returns the response to it—neither the scope token (§3.4, §3.14.3) nor the credential of an egress destination (§3.16) ever crosses over to the Logic Container. Unlike the rest of the internal boundaries (§2.2, §3.4), **this one is not left to the implementation**: it is a concrete, named and versioned interface, and the transport it runs over is part of what its version fixes—not a choice of each node or each deployment.

**Each task of the node has a work area: a file space the two halves share, which is part of the Node Runtime Interface.** The Integration Sidecar creates it empty when it hands over the assignment and deletes it when the task closes; a root a channel opened has its own until the channel closes it (§3.5.4). If the session with the Logic Container drops, it deletes them all, because a Logic Container that reconnects starts with no tasks. It is the disk the Logic Container works its task on and the medium by which a body crosses the node's boundary: that of an egress call goes out from there, and that of its response comes back there (§3.16.2). What has to survive the task or reach another node, the Logic Container writes to the Context Store (§3.4).

**Each message a channel admits through its ingress has a message area**, with the bodies it brought, from when the Integration Sidecar admits it until the Logic Container resolves it (§3.16.7). The Logic Container reads it, and the Integration Sidecar deletes it when the message is resolved or the session drops, like the work areas.

**The Logic Container reaches nothing outside that interface.** It is the flip side of §2.2: the network does not see into the node, and the node does not reach out except through the declared boundary. It reaches no destination through a channel of its own, resolves no credentials, talks to no store and mounts no filesystem of the projects the network operates on (§2.4)—what reaches the user's machine is egress like any other and goes where everything else goes (§3.16). **The channels it does have are declared**, and the Node Runtime Interface is the only one: confinement is evaluated as a predicate over that declaration and not over the artifact's behavior. What is fixed is the contract and not the mechanism that achieves it: what form that isolation takes is a deployment decision, with the same degree of freedom that §3.14.1 gives transport identity.

That is what turns into properties, and not conventions, what would otherwise depend on the Logic Container behaving: the scope token (§3.14.3), the capability credential (§3.14.2), the credential of each destination and the node's `egress_grants` (§3.16) are not reachable from inside. **What it bounds is what the node reaches, never how much it asks for of what it has been granted:** a compromised Logic Container can abuse the calls its entries allow it, and that is contained by the metering of §3.10 and the budget of §3.15, not by this boundary.

**Why "implementation detail" is not enough here.** The criterion that frees the other internal boundaries—whoever implements both sides deploys them together—is the only one that does not hold here, and the asymmetry is deliberate: the Logic Container is stored as an immutable pointer in the Specialty Catalog and can be revived much later (§3.13.3), while the Integration Sidecar is versioned and deployed by whoever operates the substrate, without going through any blueprint. The two halves of the node therefore have **independent lifecycles by design**, so an old Logic Container paired with a new Integration Sidecar is not an edge case but the normal case in the medium term. With the mechanism left free, an image built against one channel shape would not start with an Integration Sidecar that speaks another, and the failure would show up at runtime on a node the network already counts as coverage.

**The rule that makes compatibility cheap: the Integration Sidecar widens what it does, never what it demands.** Within the same major version, the Integration Sidecar can add responsibilities over the event it carries—the `task_embedding` it stamps (§3.7.4)—because a Logic Container that does not know them keeps working without noticing. What it cannot do without breaking the major version is widen what it *asks* of it: a new field in what the Logic Container returns, a new phase of the exchange, a change of shape in what it already hands it. It is not a style convention—it is what lets this interface grow without invalidating any blueprint, and lets the window of supported versions be short without becoming restrictive.

**And since it is also the edge that confines the Logic Container, widening it is not free.** Each capability added to it is **permanent** attack surface: by the rule above, what is offered once has to keep being offered, and by the independent lifecycles further down, a blueprint revived much later will find it available. The discipline that follows is that the interface grows for what a node cannot resolve any other way, never for the convenience of a particular blueprint—which is why it covers categories of need (getting context, calling out, publishing) and not domain verbs.

* **Version declared per blueprint, range declared by the substrate.** Each Logic Container declares the interface version it was built against, and that version is copied into the Catalog entry (§3.13.3) so that the Spawner can read it **before** instantiating anything. The range the deployed Integration Sidecar supports is `runtime_interface_range` (§2.3), provisioned together with the Integration Sidecar itself. It is a range and not a version because the blue/green of §3.13.4 runs original and candidate **in parallel**: the Integration Sidecar has to speak both at once, not just tolerate an old one when reviving it.
* **The check lives in two layers, just like the egress of §3.16.** The Spawner evaluates it as a provisioning precondition—a predicate over identifiers, without reading anything inside the container (§3.13.1)—and does not provision out of range; and the Integration Sidecar itself rejects at startup a Logic Container whose version it does not support, before the node subscribes to any topic or emits a single `task.proposed`. The Spawner's layer makes the failure early and legible; the Integration Sidecar's, safe: **an incompatible blueprint never gets to compete for a task**, not even if the configuration declares a range the deployed binary does not meet.

#### 3.6.2. Emission by semantic nodes (with an LLM)
When a semantic node—one that requires reasoning to solve its task—needs to publish an event, the decision to emit it is made inside its Logic Container (§3.6.1), using native capabilities of the LLM's API or the orchestration that blueprint implements:

* **Function Calling (Tool Use):** The LLM is given a virtual "tool" in its System Prompt (e.g. `emit_task()`). When the model decides to invoke this tool with specific parameters, the Logic Container intercepts the call, formats the JSON and hands it to the Integration Sidecar to publish.
* **Structured Outputs (JSON Mode):** Smaller or local models that do not support complex function calls are forced to answer strictly under a predefined JSON Schema. The Logic Container validates the structure of this JSON and hands it to the Integration Sidecar.
* **Multi-step orchestration:** none of the cases above assumes a single LLM call—a Logic Container implemented as a state graph can go through several phases, tools and internal retries before deciding which event to hand to the Integration Sidecar. That complexity is internal (§2.2) and does not change the contract with the Integration Sidecar, which stays the same: zero, one or more events at the end.

In no case do the LLM or the Logic Container talk directly to the Bus—the Integration Sidecar still exclusively controls that boundary (§3.6.1). Nor do they talk to the model provider: how many times to call it and with what prompt is the blueprint's decision, but the Integration Sidecar executes each of those calls on its behalf (§3.16), whether the blueprint is a single call or an entire state graph.

#### 3.6.3. Emission by deterministic nodes (without an LLM)
There are nodes in the swarm that require no artificial intelligence, operating with millisecond latency and **zero token cost**. Their Logic Container (§3.6.1) is simply the business script, with no reasoning engine inside; the Integration Sidecar that accompanies it is identical to that of any other node. These nodes generate events based purely on business rules and logical results:

* **Pure business rule:** a script that translates a logical result—the exit code of a process, an API response, a predicate over the input—into `task.completed` or `task.failed`, without consulting any AI.
* **User-Proxy:** the entry edge of §3.5—an HTTP service that generates the `TraceID` and hands the founding `task.announced` to the Integration Sidecar, without making any semantic decision (§3.5.1).
* **General pattern: human-backed node.** The User-Proxy is the structural case of a broader pattern, not an isolated case: a deterministic node can route the decision to an external human instead of applying business rules—its Logic Container reasons about nothing, it only packages the input, waits for the answer from the person on the other side (a ticketing dashboard, an approval queue, whatever it is) and reports it to the Integration Sidecar. It is still deterministic in the sense that matters here: semantic reasoning happens outside the node, never inside its Logic Container (§2.2). Any domain specialty can have a worker built this way—a human escalation node subscribed to a domain topic, for example—competing and being created/archived by the Spawner exactly like any other node (§3.7.1), without the network needing to treat it differently.

**Zero cost survives these nodes decomposing work.** A deterministic node can publish subtasks like any other (§3.7.4), and every `task.announced` carries a `task_embedding`—which would seem to force it to call a model and contradict the sentence above. It does not happen, because that generation belongs to the Integration Sidecar and not to the Logic Container (§3.6.1): the business script hands over the event without an embedding and it comes out embedded on the other side of the local boundary. "Zero token cost" refers to what it costs to *solve the task*, which is what `metrics` aggregates (§3.10), and it remains literal: the embedding is a call the Integration Sidecar originates on its own, not one the node asked for.

The combination of both subtypes over the same Integration Sidecar contract is what yields cost-efficient hybrid routing; §5.2 walks through it step by step on a concrete request.

#### 3.6.4. Delivery guarantees and idempotency

The Bus delivers events **at-least-once**, never exactly-once: given any doubt about whether a publication was confirmed (e.g. the Integration Sidecar crashes between emitting `task.completed` and receiving the Bus's ACK), the system prefers to retry and risk a duplicate rather than risk losing the event. This guarantee is split into two responsibilities that live in different processes (§3.6.1) and do not know each other:

* **Integration layer (Integration Sidecar, §3.6.1), the same for every node:** before trying to publish, the Integration Sidecar persists the event in a durable local buffer and retries the publication until it confirms the Bus's ACK (an *outbox* scoped to the Integration Sidecar itself, not to the node's Logic Container—it lives in the private volume the provisioning act produces for it, §3.13.1)—so a crash halfway never loses the event, at most it duplicates it. On receiving, the Integration Sidecar deduplicates by the envelope's `id` (§3.8.1) against the events already processed **before** forwarding it to the Logic Container. This layer is blind to the node's content: it does not need to know whether the node is semantic or deterministic (§3.6.2, §3.6.3); it only moves the event.
* **Internal implementation layer of the node (Logic Container, §3.6.1), specific to each blueprint:** deduplicating the *delivery* of the event does not guarantee that the *effect* of processing it happens only once—that depends on whether the action the node triggers is safe to repeat. A node whose action is a pure function with no external effects (running the same computation on the same input always gives the same result) is already idempotent by construction and needs nothing additional. A node whose action has non-repeatable external effects (creating a branch/commit/PR, sending a message, moving money) must implement its own duplicate check in its domain (e.g. before creating a PR, checking whether one associated with the same `TaskID` already exists)—something the Integration Sidecar cannot do for it without knowing that domain, and that the system cannot verify from outside (§2.2). It is an obligation of every Logic Container that has external effects, and the Bus does not cover it.

#### 3.6.5. Bus contract

§3.6.4 fixes the delivery guarantee; this section fixes the rest of what the Bus promises a node. It is deliberately a minimal contract: everything the Bus does *not* guarantee is resolved elsewhere, and adding strong guarantees to it here would make several of the possible implementations of the substrate unviable without buying anything the network needs.

* **Subscription by topic, fan-out delivery per node.** Every subscriber of a topic receives **its own copy** of each event and decides on its own what to do with it (§3.7.5). That is what makes the auction exist: if the Bus split a `task.announced` among the subscribers instead of giving it to all of them, there would be no competition to arbitrate. It holds equally for a `task.announced` and for a `notice` (§3.8.2), and the Bus does not need to discriminate by event type.
* **The unit of capacity and of competition is the node, and that is how the network scales.** A node works one task at a time (§3.6.1), so a niche's throughput does not grow by enlarging a node from inside but **by having more nodes**: a blueprint instantiated twice is two nodes, each with its own deployment and its own row in the Active Node Registry (§3.11), which compete with each other through the normal mechanism just as they compete against any other. The Bus has nothing special to do with that case—they are two more subscribers. **The Spawner decides whether to bring them in, and the criterion belongs to §6** (§3.13.2); what this section fixes is that the substrate does not prevent it.
* **A late or duplicate `notice` breaks nothing, but it is not always free.** Delivery is still that of §3.6.4—at-least-once, deduplicated by `id`—and since a notice obliges nothing, a duplicate is harmless and a late one is indistinguishable from a duplicate. What should not be confused is whom that protects: the invariant of §3.8.2 guarantees that **the system** does not depend on delivery, not that acting on an old notice is free for **the node** that decides to believe it. A node that cancels itself because of an already outdated notice pays for the wasted work and a reopen of its lineage (§3.3), which also accumulates against the trace's budget (§3.15.1). It is a bounded and voluntary consequence—whoever watches a broadcast topic chooses to do so—and the node has no way to verify the authoritative state on its own: the stores that back a notice are read by structural components, not by nodes (§3.15.2).
* **A node claims a single topic, and the Bus is not what enforces it.** The invariant belongs to the network (§2.1) and its reason is one of governance, not of transport: ownership of a node's lifecycle is per topic (§3.13.1), so one that competed on two would have two owners able to archive and replace it for opposite reasons, over niche state neither of them shares (§3.13.3). The Bus, on the other hand, imposes no maximum on subscriptions—it is a substrate, not a contract arbiter—so the one that enforces it is whoever provisions: the Spawner derives one blueprint per niche and fixes its topic (§3.13.1, §3.13.3). A node actually subscribed to a second topic is not widening its specialty: what Layer 1 of the matching (§3.7.2) and the Spawner's vacancy check (§3.13.2) read is the topic the blueprint declares, not the traffic the node receives, so the network does not count that coverage as such and fires vacancy anyway. What does remain the blueprint's decision is **how wide** the specialty is within its topic, and there the node pays the consequences through the normal mechanism: an embedding that covers a wider semantic region wins fewer auctions (§3.7.5) and a score that averages heterogeneous performances (§3.12.2) exposes it to replacement like any other. It is the same criterion as §2.2—the network observes the external contract and the resulting quality; it does not dictate how the node organizes itself internally.
* **No ordering guarantee across topics, and none the network needs within one.** The Bus promises no global order. It may preserve it within a partition if the implementation offers that, but **no rule of the architecture depends on it**: the CNP cycle (§3.8.2) is a cycle of states the Task Broker arbitrates atomically and single-threaded per partition (§3.1), not a sequence reconstructed from arrival order; the trace hierarchy is reconstructed from `traceparent`, not from the order of observation (§3.2); and each parent upholds the closing rule of §3.9.1 against its own children. An event that arrives late or out of order is indistinguishable from a duplicate, and it is resolved with the same deduplication by `id` of §3.6.4.
* **Retention: enough for the retry, not a source of truth.** The Bus retains events for as long as a failed consumer needs to recover them when it comes back. It is configuration of the Bus, not of the network: it is not in §2.3 and no component queries it, because no network rule depends on its value. What the Bus is **not** is the network's memory: assignment state lives in the Task Broker (§3.1), the trace's history in the Tracing Collector (§3.2, §3.10), the heavy context in the Context Store (§3.4), the budget totals in the Contention Registry (§3.15.2) and each node's metering in the Network Monitor (§3.12.1)—precisely so that none depends on how much the Bus retains. Replaying the Bus from the beginning does not rebuild the network; reading those components does.
* **Topic naming.** Topic names are **stable ASCII slugs in `snake_case`**, lowercase and a single term (`coding`, `code_review`, `hitl_contact_operator`). They are not natural language and are not translated (§3.5.1): they are namespace identifiers over which Layer 1 matching runs (§3.7.2), and their readable description—the one that does carry a language and the one embedded for deduplication—lives in the Topic Registry (§3.7.6), not in the name. **A topic name is atomic:** the network derives no relation from the shape of the name, so `code_review` and `code_style` are as independent of each other as of `billing`, and no subscription reaches a topic by the resemblance of its name to another. This is what lets the substrate address any topic as a unit, however compound the term the network has minted. The only internal structure a name carries is that of `hitl_contact_<audience>`, where the suffix identifies the audience, and §3.5.3 explains why.

### 3.7. Task assignment and node self-selection

#### 3.7.1. Design principles
* **Hyper-specific nodes:** The "strict scope" is one of *specialty*, not of *task instance*: a node is not a generic "coder" but, for example, a "Python coder specialized in APIs with FastAPI". A node is not created for each one-off task—a node is created for each narrow specialty, and that same node competes for all the future tasks that fall within its competence—a reusable role, not an ephemeral instance (§2.1). If a node spans too many competences, the problem lies in the Spawner, not in the node. This keeps a single capability embedding from diluting into a blurry semantic centroid.
* **Reuse as a consequence of narrow scope:** because building a specialized node has a cost (deriving its blueprint, generating and signing its embedding, building and publishing its artifact—see §3.13.3), the Spawner does not treat it as disposable after one task: it keeps it active while there is demand for its specialty, and archives it (does not delete it) when that demand stops, so it can revive it if the demand comes back.
* **Task quality:** If a task's embedding turns out vague, the problem belongs to the node that generated the task, which has to refine the specification. The system must not create nodes for ambiguous requests.

#### 3.7.2. Two-layer matching
* **Layer 1—Topics (deterministic):** Each node subscribes to a task channel according to its nature (`coding`, `testing`, `integration`)—to a single one, which is its whole specialty (§2.1). It reduces the search space: a verifier does not evaluate implementation tasks.
* **Layer 2—Semantic similarity (embeddings):** Within its topic, each node computes the cosine similarity between its own capability embedding and the task's embedding to decide whether the task falls to it. It does not run on every topic: in the `hitl_contact_*` family Layer 1 is enough on its own and Layer 2 is exempt (§3.7.5, step 4).

#### 3.7.3. The capability embedding
* When creating a node, the Spawner assigns it an embedding generated from the description of its specific functionality.
* This embedding accompanies the node throughout its lifecycle.
* **Cross-cutting requirement:** a change of vector space (§2.3) invalidates at once everything the network generated under the previous one—capability, task and topic embeddings (§3.7.6) stop being comparable with each other. The whole system must be able to regenerate them, not only the capability ones; the `model_id` that travels in each payload and in each signed credential (§3.7.5, §3.14.2) is what makes the mix detectable until the regeneration has finished. Several pieces meet that requirement, each over a different population: §3.6.1 for task embeddings (the Integration Sidecar reads the current space, so they switch over on their own), §3.13.3 for the Catalog and the Topic Registry (convergent on-demand repair) and **§3.13.7 for the active fleet**, which is the only one that requires a procedure.

**What the `model_id` identifies: the vector space.** A cosine means something only if both vectors came out of the same space, so the identifier names everything that determines the vector from the text—**the model, the egress entry through which it is reached and the task-prefix convention under which the vector was generated**. The convention is there because matching is asymmetric: it compares the embedding of a `capability_text` against that of a task text (§3.7.5), and embedding models handle that case by prepending a different prefix to each side. Two vectors generated under different prefixes are not comparable even if the model is the same. **The identifier carries the whole convention and not the prefix each side applied**, which is what lets the Spawner and the Integration Sidecar derive the same `model_id` while each generates its own half.

**Whoever generates derives it, from the configured value.** The `model_id` is a deterministic function of `embedding_model` (§2.3), which only the operator edits (§3.14.4). Every generator reads the same key, so two generators under the same value derive the same identifier without coordinating, and a vector generated under the previous value while the change propagates is given away by the difference.

**It identifies the space as firmly as the configuration names the model.** An Embedding Model that starts serving another artifact under the same name redefines the space without the identifier changing, and no component detects it. Naming the model by an identifier that pins the artifact—a digest, where the runtime exposes one—closes this gap, and that is the decision of whoever configures the key.

**An embedding is a cache, not primary data.** The cross-cutting requirement states that the system "must be able to regenerate them", and wishing does not make it so: a vector, in isolation, cannot be recomputed in another space. The rule that makes it mechanically true is one of persistence, and it governs **every** embedding the network keeps beyond a single event:

* **The triple `{source_text, model_id, vector}` is persisted,** where the vector is a pure function of the source text and the `model_id`. It applies to a blueprint's capability embedding (`capability_text`, §3.13.3) and to that of a Topic Registry topic (§3.7.6). Regenerating under another model stops being a data migration and becomes recomputing a cache from an input that was never lost.
* **The source text cannot be re-derived from the other fields, which is why it is stored explicitly instead of being reconstructed.** It is not always a description of what the vector represents: that of a topic is the text of the task that originated it (§3.13.2), which no other field preserves. Regenerating from a newly chosen text, instead of the original, would move the vector without anything recording it.
* **The triple stays consistent or it means nothing.** Editing the text without recomputing the vector leaves the node competing with a semantics that is no longer the one it declares, and nothing external would detect it: the `model_id` would match. Text and vector are written together, in the same operation that provisions or updates the blueprint.

**And a rule of use, not only of persistence: no vector is ever compared against another unless both `model_id` values match and are the current one.** The cross-cutting requirement says the `model_id` "is what makes the mix detectable", but detectable is not detected: stating the property obliges no one to exercise it. The Task Broker exercises it—it discards the proposal whose `model_id` does not match before recomputing anything (§3.7.5, step 4)—and that check is not a special case of the award path but the most visible instance of a rule that governs everywhere. Where a comparison between different spaces is not rejected, it returns a plausible number nobody validates, and the damage is proportional to what that comparison decides. §3.13.3 instruments the rule for the other place where a comparison decides something: the neighborhood searches with which the Spawner decides coverage.

This rule is also what lets a blueprint cross a network's boundary without dragging along the vector space of its network of origin (§3.13.6).

#### 3.7.4. The task embedding

The task embedding is a self-selection tool: it lets each node, without knowing the rest of the network, decide whether it should propose for a piece of work. It is not a global ranking mechanism ("am I the best candidate?") but a local filter ("is this within my competence?"). Its generation rules derive from that purpose:

* **Who generates it:** it is not the exclusive attribution of any role (§2.1)—*the node that publishes the `task.announced`* generates it, whatever that role is. That includes the Entry Node (User-Proxy) publishing the root request, or any worker that decomposes its work into subtasks and announces them as new `task.announced` events.
  * **Which half of the node:** the **Integration Sidecar**, not the Logic Container (§3.6.1). The Logic Container decides *which* task to announce and with what text; the Integration Sidecar derives the vector from that text when publishing. That is what lets a deterministic node (§3.6.3) announce subtasks without a client for any model, and what keeps any blueprint from carrying a dependency on the embedding model.
  * **Under which space:** the **current** `embedding_model` (§2.3), read by the Integration Sidecar at publishing time—never the one pinned by `config_version` in the envelope. The distinction is deliberate, and §2.3 argues it when classifying that parameter. The Integration Sidecar prepends to the task text the prefix that the convention of that space reserves for the querying side (§3.7.3), and the `model_id` of the space it generated under travels in `data` next to the vector (§3.8.1), which is what lets the Task Broker detect the mix (§3.7.5, step 4).
* **Which text:** the announcement's text decides who competes, because from it comes the vector against which each node measures its floor (§3.7.5). It describes the work requested, at the granularity at which the emitter wants competition, and the material being worked on goes to the Context Store by Claim-Check (§3.4). An emitter that announces a closed set of jobs on a topic can use a fixed text per job and declare them in its blueprint (§3.13.6): the vector stops depending on the material, a text written by a third party does not shift who claims the task, and a bundle's closure can check that the claimant wins the announcement.
* **When it applies:** the embedding only makes sense in open broadcast events (`task.announced`, the CNP `cfp`), because they are the only ones that require multiple nodes unknown to each other to select themselves. An event addressed to a specific node—`task.assigned` and `task.rejected` toward whoever proposed, `task.completed` and `task.failed` toward the requester that opened the task—needs no `task_embedding`: the recipient is already resolved, by the proposal in one case and by the announcement's `requester_identity` in the other (§3.8.1), and there is nothing to match.
* **Regenerating vs. reusing:** the rule is whether the semantic content of the task changed, not whether the event changed.
  * **It is regenerated** when the re-publication implies a respecification: for example, a `task.failed` that leads to reopening the task with a more precise description (including the traceback or the cause of the failure)—whoever emits that new `task.announced` generates a new embedding, because the text describing the task is no longer the same.
  * **It is reused** when the re-publication does not change the task's description, only its declarative metadata: the typical case is a re-announcement that only increments `current_attempts` (§3.3) because the request itself is identical and the only thing that changed is how many times it was attempted. It is still a `task.announced` like any other—what decides is whether the semantic content changed, not the event type—and it is already covered by "when it applies". Reusing the original embedding avoids an unnecessary regeneration, in the same spirit as reviving nodes to reuse their embedding (§3.7.1). An embedding whose `model_id` is not the current `embedding_model` is never reused: it is regenerated even if the text is the same (§3.7.3).
* The embedding travels in the event payload (a lightweight vector), together with the `TraceID` and the Claim-Check reference to the heavy context.

#### 3.7.5. Decision flow
1. The node listens to its topic constantly, waiting for `task.announced` (the CNP `cfp`, see §3.8).
2. It computes `cosine_similarity(agent_embedding, task_embedding)`.
3. **Similarity floor (local filter), and only if the node is free:** the Integration Sidecar publishes `task.proposed` only when the node has no task in progress (§3.6.1, capacity rule, which does not govern a `hitl_contact_*` channel) **and** the similarity exceeds its credential's `similarity_floor` (§3.13.3, §3.14.2). The Integration Sidecar evaluates this itself, since it already holds that credential, the signed embedding it carries inside and the node's busy state (§3.6.1). For either of those causes the node does not propose—and there lies the distinction this step upholds: "no one is an appropriate candidate" versus **"no one decided to compete"**, which covers both the node that does not reach the floor and the one that is busy. Both leave the task legitimately vacant in step 5, and the one that separates them afterwards is the Spawner looking at the active fleet (§3.13.2), not the Task Broker. When the announcement passes, the Integration Sidecar publishes the proposal with the similarity it computed, without consulting the Logic Container (§3.6.1); the computation is a traffic filter, not the award criterion.
4. **Recomputation and award (authority):** the Task Broker does not award by the number the node declares. For each `task.proposed` it recomputes `s_calc = cosine_similarity(signed_embedding, task_embedding)`—the embedding comes from the credential signed by the Spawner (§3.14.2), the `task_embedding` from the task state the Task Broker already holds (§3.1)—and awards by `s_effective = min(s_reported, s_calc)`. The signature thus acts as a ceiling: the similarity a proposal declares can lower the one its credential allows, never raise it. The Task Broker applies that same credential's `similarity_floor` to `s_effective` (the node's check is an optimization, not the guarantee) and grants the task to the highest through `task.assigned` (atomic operation); it answers the rest with `task.rejected`.
   * **Each proposal is judged against its own floor, and the floor decides admissibility and never order.** Nodes with different floors thus compete in the same auction without the Task Broker resolving any floor against the configuration or checking one against another, and a wide floor beats no one: it only admits its node to tasks where one with a narrow floor would have stayed silent. Hence a broad-coverage node loses against any specialist in its region and wins where there is none, with no dedicated rule.
   * For both ends to give the same number, embeddings are stored and signed **normalized** (the cosine reduces to a dot product) and the comparison against the floor is done with rounding to `similarity_precision_decimals` (§2.3). Without that, a last-bit difference decides arbitrarily at the edge of the floor.
   * **"The highest" is evaluated over the rounded `s_effective`, and so there can be more than one.** Rounding is not only for the floor: if the network declares that beyond a certain decimal it does not distinguish two similarities, it cannot afterwards assert that at higher resolution one beats the other—it would be exercising a precision it declared itself not to have. The set of proposals that tie at that rounded value is then a legitimate equivalence class, and **the Task Broker chooses within it by draw**. Arrival order does not work: it is the variable that has least to do with the competition and correlates most with deployment details.
     * **The draw is deterministic, seeded by `TaskID`:** the highest `hash(TaskID, node_id)` of the tied set wins. It is the only way to have these properties at once—over many tasks the work is spread uniformly among the tied nodes, and yet the award **remains recomputable from the trace**, which is what §3.1 asks of the Task Broker and what a `random()` would break. It adds no round trip or state: it is a pure function of the set of proposals the Task Broker already has at hand when it awards, so the operation remains atomic.
     * **Rounding is applied after the `min`,** on `s_effective` and not on `s_calc`. The other way round, a proposal would enter the tie by a declared value higher than the recomputed one, and the ceiling would stop being one.
     * **This is what keeps a tie from always going to the same node,** and the blue/green of §3.13.4 depends on it: a candidate provisioned on the niche of a node that already covers it might never receive a task, never reach `min_observations` and leave the replacement without converging. The Task Broker still does not know a replacement is in progress (there is no dedicated rule and no exception by node type); what there is, is a general award rule that, incidentally, stops being biased. The most frequent live case is that of a revived blueprint, whose triple comes back intact from the Catalog (§3.13.3) and therefore ties exactly with its neighbor's.
   * The Task Broker discards the proposal if the credential's `model_id` does not match that of the `task_embedding`: they are vectors from different spaces and their cosine means nothing. Detecting it is its responsibility, because it is the one that recomputes.
   * The Task Broker also verifies that the credential's subject is the platform identity the deployment attributes to the event (§3.14.1). Since the credential is static and travels in every proposal, without that check a node could replay another node's better-matched credential. For the same reason it can cache the credential by identity and not re-verify the signature on every proposal.
   * **Exception: structural components do not go through this step.** The rule, in its general form:

     > Given a `task.proposed` published by a **structural component** (§2.1), the Task Broker verifies the signature and the correspondence with the platform identity that published the event; **it does not recompute similarity, does not apply a floor and does not discard for a mismatched `model_id`**, and it ranks the proposal by the `s_reported` it declares.

     The rule applies when the candidates are interchangeable (there is nothing the similarity recomputation could rank among them) and, at the same time, the proposer's credential does not depend on any internal component of the network, so a change of the embedding model (§2.3) cannot invalidate it. These paths meet both conditions:

     * **The `hitl_contact_*` family** (§3.5.3): the topic names the audience, and every channel subscribed to it serves it by definition, so there is no competition to rank—all candidates are equally competent, and the blueprint's `attempt_window` (§3.5.2) and the atomic award already settle the choice among them. On these topics the Task Broker verifies the signature, the correspondence with the platform identity that published the event and, in an emergent channel, the operator's proof against the deployment root (§3.14.2): that is the real admission barrier. It admits only channel credentials of that audience—the deployment's that serves it, or an emergent one with a proof—so the Spawner's sentinel proposal does not get in here: the Spawner closes a vacant query without taking it (§3.13.2). The `task_embedding` still travels in the announcement (§3.7.4), but it takes no part in admission. The `hitl_contact_operator` credential in particular comes provisioned with the deployment and nothing inside the network can re-issue it (§3.14.2), so if the Task Broker recomputed similarity here, a model change would leave discarded for a mismatched `model_id` precisely the proposals of the channel that authorizes that very change.
     * **The fixed-convention topics with a structural claimant** (§3.7.7): `config_change`, `trace_query`, `node_review`, `node_query`, `node_catalog_query`, `node_catalog_publish`, `node_catalog_import`, `node_provision`, `node_create`, `node_retire` and `topic_catalog_query`. In none of them is there competition to rank—either the owner is unique by deterministic routing, or the candidates are interchangeable because they answer by reading a shared store—and in all of them the credential comes provisioned with the deployment instead of being signed by the Spawner. Without this rule, a change of `embedding_model` (§2.3) would leave the Task Broker discarding the proposals of the Config Store, the Tracing Collector and the Spawner precisely in the window where administering the network, querying its history and repairing the vector space (§3.13.3) is the only thing that has to keep working.
     * **The Spawner's sentinel proposal on a vacant emergent topic** (§3.13.2): it is the only structural path that does not go through a fixed-convention topic, and that is why a rule stated per topic would not cover it. Here the effect would be permanent, not transient: the Spawner's credential, like that of every structural component, comes provisioned with the deployment and nobody inside can re-issue it (§3.14.2), so its `model_id` stays fixed forever. Once the model changed a single time, the Task Broker would discard all its proposals and the Spawner would never win a vacancy again—bringing down with it node creation, the cold population of `intake` (§5.1) and the very repair the model change requires.

     **How the Task Broker knows the proposer is structural.** The distinction is cryptographic: both credentials verify against the same root of trust, and what separates them is the depth of the chain (§3.14.2). A structural component's credential comes provisioned with the deployment and verifies directly against the root; an emergent node's does so through an intermediate link—the `spawner` role certificate of whoever signed it—which is precisely what marks it as emergent. The Task Broker does not choose which key to verify against or consult any table: it verifies a chain and reads its shape. An emergent node trying to pass itself off as structural would need a credential signed by a root that nothing inside the network can issue—the same property that ensures a compromised Spawner cannot mint operator authority for itself. The envelope's `source` takes no part in this decision.

     **The predicate evaluates the class of the proposer, not a specific identity, meeting the constraint of §3.13.1 and §3.13.2 against rules dedicated to the Spawner.** It applies equally to all the paths above, and the Spawner's sentinel is covered as one more case, with no logic of its own: it proposes declaring the lowest possible similarity, and with `s_calc` absent `s_effective = min(s_reported, s_calc)` is still that minimum, so the usual rule—the highest wins—still automatically prefers any legitimate candidate that shows up in the same round. A structural component declaring itself high buys nothing—its credential is of verified provenance, and overbidding would only make it win tasks it then fails—and the `model_id` on this path never decided anything: it could only break it.

     **The dividing line is the claimant, not the topic.** `intake` is also fixed-convention, but an emergent role claims it (§3.7.7): there similarity does decide among candidates that are not interchangeable, and step 4 runs in full. A fixed topic is not exempt for being fixed; it is exempt for having nothing to rank—and, symmetrically, an emergent topic does not require ranking when the proposer is the structural component that exists precisely to cover what nobody covered.
5. **Vacancy:** if no proposal exceeds its floor within the auction timeout (`auction_timeout`, Global Configuration, §2.3), the task returns to `UNASSIGNED` and the Task Broker re-announces it with backoff (§3.1). The Spawner, which observes this situation passively, decides when and how to intervene—see §3.13.2 for the full mechanism.
   * On `hitl_contact_*`, where there is no floor to exceed, vacancy simply means that **nobody proposed** within the timeout—and since a channel does not stop proposing because it has pending queries (§3.6.1), it means that no live channel of the audience is eligible in that round. The state transition and the re-announcement are the same; both the `attempt_window` of §3.5.2 (a round with no enabled channels expires through here, cheaply) and the Spawner's vacancy branch (§3.13.2) depend on that.

#### 3.7.6. Topic governance: registration, deduplication and query

The `topic` space is open by design (§3.8): any node that decomposes its work can mint a new topic when publishing a child `task.announced` (§3.7.4), without coordinating with the rest of the network. Left ungoverned, this risks semantic fragmentation—`coding`, `programming` and `develop` coexisting as distinct topics, each with its own node, when in reality they are the same work artificially split. That risk is closed by reusing patterns that already govern elsewhere in the network, without adding new structural components.

* **Two populations of topics:** the **fixed-convention** ones (`intake`, §2.1, is the only one the architecture requires as a component in its own right) are established when the network is deployed and go through no check—their full inventory and their contracts are in §3.7.7; the **emergent** ones are all the others, minted dynamically as the network decomposes work, and they are the ones this mechanism governs.
* **Optimistic emission, centralized authority:** a node that decides to publish on a new topic needs no permission and consults nothing before doing so—an invented topic nobody claims is as cheap as any other topic without candidates (§3.7.5, vacancy). The only authority that actually *mints* a topic is the Spawner, and only at the moment it is about to pay the real cost of creating a node for it (§3.13.2, missing-coverage branch, step 2). Nodes propose topics; the Spawner decides which ones actually come to exist.
* **Topic Registry:** an extension of the Specialty Catalog (§3.13.3)—the same store shared among all of the network's Spawner partitions, not a new component. Each entry is `{topic, embedding, model_id, description}`—the `description`, a short description, is the **exact source text** from which that embedding was derived (§3.7.3), not a separate gloss written for human consumption. It is written only once, in step 2 of the missing-coverage branch of §3.13.2, when the Spawner confirms that a topic is genuinely new and creates the first node for it.
* **`topic_catalog_query`: optional query on the emitting node's side.** A node that is about to decide which topic to dispatch a subtask to—typically when decomposing a request into more specific subtasks (§3.7.4)—can, if its own blueprint implements it, publish `task.announced` on the dedicated topic `topic_catalog_query` (§3.8) to ask for the current listing. Any Spawner instance can answer—unlike `trace_query` (§3.10, scoped by `TraceID`) or `node_review` (§3.12.3, scoped by `target_topic`), the Topic Registry is already shared among partitions (§3.13.3), so no deterministic routing is needed: it is resolved by **auction without similarity** (admission by structural credential, §3.7.5 step 4), because any instance is equally competent to answer. Ranking by neighborhood would not choose better among interchangeable candidates and would set the Spawner competing against the same vector space it repairs (§3.13.3), breaking this query precisely when the model is changing. The listing (names + descriptions) is lightweight and travels directly in the payload of the `task.completed`, with no need for Claim-Check.
* **Coordination cost:** the general criterion of §3.10 applies—it feeds a node decision, not the critical path. And the marginal cost is even lower than that of `trace_query`: a semantic node that is going to invoke its LLM anyway to decide how to decompose the work only needs to add the listing to the context of that same call—it does not trigger an additional model call; it only enriches it.
* **Heuristic, not authority:** querying `topic_catalog_query` reduces how often a node ends up proposing a redundant topic, but does not guarantee it—the listing may be out of date, or the node's criterion may fail anyway. The Spawner's neighborhood check (§3.13.2, missing-coverage branch, step 1) is still the final authority and always runs, whether or not the emitting node queried. A network can operate without any node that implements this query—more vacancies, more coordination cost, but without compromising the system's correctness (the same principle of emergent composition as §2.1).

#### 3.7.7. Fixed-convention topics

§3.7.6 divides the topic space into two populations and governs the emergent one. This section closes the other: the topics that exist **by convention, not by minting**—they are established when the network is deployed, do not go through the neighborhood check, do not enter the Topic Registry, and no node can rename or deduplicate them. Each is born where its mechanism is born; here is the full inventory and what each one guarantees.

| Topic | Who claims it | Mechanism | If nobody claims it |
| :--- | :--- | :--- | :--- |
| `intake` (entry topic) | the first domain node that proposes | auction (§3.7.5) | vacancy → the Spawner provisions (§5.1) |
| `config_change` | Config Store (§3.14.4) | deterministic routing | does not happen: it is structural (§2.1) |
| `trace_query` | Tracing Collector of the `TraceID`'s partition (§3.10) | deterministic routing, scoped by `TraceID` | timeout visible to the requester (§3.10) |
| `node_review` | Spawner of the `topic`'s partition (§3.12.3) | deterministic routing, scoped by `target_topic` | does not happen: it is structural (§2.1) |
| `node_query` | Network Monitor—the one of the `topic`'s partition in the point form, any instance in the active-fleet census form (§3.12.3) | deterministic by `data.target_topic`; without it, auction without similarity | timeout visible to the requester (§3.12.1) |
| `node_catalog_query` | any Spawner instance (§3.13.3) | auction without similarity—the Catalog is already shared | timeout visible to the operator: they cannot choose what to promote or what to delete, and nothing else is affected (§3.13.6) |
| `node_catalog_publish` | Spawner of the partition of the blueprint's `topic`; any instance if the request names a bundle (§3.13.6) | deterministic by `data.target_topic`; without it, auction without similarity | timeout visible to the operator: the promotion does not happen and nothing else is affected (§2.1) |
| `node_provision` | Spawner of the partition of the blueprint's `topic` (§3.13.8) | deterministic routing, scoped by `target_topic` | timeout visible to the operator: the instantiation does not happen and nothing else is affected (§2.1) |
| `node_create` | Spawner of the partition of the `topic` the node is going to claim (§3.13.8) | same | timeout visible to the operator: the entry is not registered and nothing else is affected |
| `node_catalog_import` | Spawner of the partition of the blueprint's `topic`; any instance if the request names a bundle (§3.13.8) | deterministic by `data.target_topic`; without it, auction without similarity | timeout visible to the operator: the entry is not registered and nothing else is affected |
| `node_retire` | Spawner of the partition of the `topic` of the node or the entry (§3.13.8) | deterministic routing, scoped by `target_topic` | timeout visible to the operator: the node keeps running or the entry stays unmarked, and nothing else is affected |
| `topic_catalog_query` | any Spawner instance (§3.7.6) | auction without similarity—the Registry is already shared | optional query: more redundant topics, without compromising correctness |
| `trace_risk` | nobody: it is a broadcast, not a task—the Tracing Collector emits it (§3.15.2) | `notice` (§3.8.2), fan-out per node (§3.6.5) | does not apply: there is nothing to award |
| `network_risk` | same: the Network Monitor and the Spawner emit it (§3.15.7) | same | same |
| `hitl_contact_<audience>` | the channel that serves that audience (§3.5.3) | auction *within* the audience, without similarity: admission by credential and membership (§3.7.5, step 4) | vacancy → the Spawner fails it without taking it, and the requester counts it as a round without an answer (§3.5.2, §3.13.2) |

What the table does not say:

* **Fixed does not mean exempt from vacancy.** A topic existing by convention only takes it out of the minting cycle (§3.7.6); auction and vacancy apply equally to those claimed by auction. That is why `intake` in a freshly deployed network triggers the Spawner like any other topic without candidates (§5.1, step 3). And there is no need to exempt the broadcast rows: no `task.announced` is ever emitted on them, so there are no rounds to count and no vacancy to declare (§3.8.2)—the rule holds with no list of exceptions to maintain.
* **`hitl_contact_<audience>` is a family, not a topic.** The prefix is fixed-convention; the suffix is one of the audiences §3.5.3 fixes and is **not** free: no node mints it, so no topic of the family enters the Topic Registry (§3.7.6). It is the only case where the suffix of a topic name carries meaning (§3.6.5).
* **The topic a request is about travels in `data.target_topic`, and `data.topic` is always that of the announcement.** The requests that name a node or an entry—`node_review`, the point form of `node_query`, `node_catalog_publish` and the operator's requests on the fleet (§3.13.8)—are announced on their topic from the table and carry in `target_topic` the topic of the specialty they name, which is the key against which their claimant selects itself. They are two fields because `data.topic` is read by consumers that do not know the event's topic—the Task Broker when choosing a partition (§3.1), the Spawner when counting vacancy rounds (§3.13.2), the Network Monitor when counting a topic's awards (§3.12.3)—and a request that put the specialty there would count as traffic of that specialty: the review of a node for `no_demand` would add an award to the topic whose lack of demand it reports. It is the rule §3.8.1 fixes for `subject`: a task's argument travels in a field of its own. A request without `target_topic`—publishing or importing a bundle (§3.13.6)—is claimed by any instance.
* **Deterministic routing is what makes an empty network administrable.** The topics claimed by routing instead of by auction (`config_change`, `trace_query`, `node_review`, `node_query` in its point form) have a structural owner from startup, before a single emergent node exists. That is what upholds the statement of §2.1 and §5.1: administering the network, querying its history and inspecting what is running cannot depend on the network being populated.
* **The claimant column splits the table, and that split decides admission.** The split is not binary. Where the claimant is a structural component, the award does not go through similarity: admission is by credential and membership (§3.7.5, step 4). Where there is no claimant—`trace_risk` and `network_risk`, which are broadcasts—there is no admission at all: a `notice` is neither admitted nor rejected because it never goes through the Task Broker (§3.8.2). And **a single topic remains where step 4 runs in full**: `intake`, the only one in the table whose candidates are not interchangeable and where neighborhood actually chooses. The practical consequence is what matters: **administration, observability and human contact do not depend on the current vector space**, so they survive a change of `embedding_model` (§2.3) just as they survive a pause, with no exceptions. The mechanisms by which an admitted fixed topic sidesteps similarity—deterministic routing and admission exemption—are not different rules but implementations of the same one; broadcast does not even need to sidestep it, because there is nothing to award.

  **And the dividing line goes beyond this table.** The criterion being the claimant and not the topic has a consequence that cannot be seen by looking only at this table's rows: a structural component is exempt **also when it proposes outside of here**. The concrete case is the Spawner with its sentinel proposal on a vacant emergent topic (§3.13.2)—structural, with nothing to rank, and with a credential that comes with the deployment and nobody can re-issue. §3.7.5 treats it in the same rule and by the same argument. Reading the exemption as a property of this table would leave that path being discarded for `model_id` permanently after the first migration.
* **The table is also the list of exemptions from the network pause.** With admission paused (§3.18), what the Task Broker keeps admitting is a subset of this table: **everything that is a task, except `intake`**. It is not a list invented for that section: the line falls where it already was, because everything else in this table is administration, observability, human contact or fleet preparation, and `intake` is the only domain work that appears in it. The operator's requests on the fleet (§3.13.8) being on that side is deliberate: instantiating coverage the network will need when it reopens is work on the fleet and not domain work, and the node brought up during the window is born signed under the current `embedding_model` (§3.13.8), so it enters the roster already migrated instead of adding to what is pending (§3.13.7). The broadcast rows are left off the list for a different and stronger reason than an exemption: a `notice` is neither admitted nor rejected, because it never goes through the Task Broker—the pause does not reach it, and not because it was exempted. A concrete consequence of `hitl_contact_<audience>` being exempt: a human query opened before the pause can close during it, instead of expiring by `hitl_response_window` (§3.5.2) while the network is stopped.

**`intake` in detail.** It is the only one in the table that §2.1 lists as a structural component in its own right—the others are topics a mechanism uses, not infrastructure that gets deployed. Its contract deserves to be made explicit:

* **Why it exists by definition.** The Entry Node is deterministic (§3.6.3) and classifying a request into a domain topic is a semantic decision that is not its to make (§3.5.1). If there were no entry topic agreed in advance, the edge would have to choose one—and that choice is exactly what the architecture forbids it. `intake` is the way out of that problem: a destination that requires no classification.
* **Who claims it.** Nobody by contract. Whoever proposes and the Task Broker chooses wins it (§3.7.5), and that node is, in practice, the first to decide what to do with the request—typically decompose it toward more specific topics. There is no reserved "Planner": the role is emergent and replaceable like any other (§2.1, §3.13.4).
* **What happens if nobody does.** Normal vacancy: backoff, re-announcement, and on crossing the rounds threshold the Spawner that owns `intake` in its ring (§3.19) provisions a node for it (§3.13.2). That Spawner exists from the first second, even though `intake` has no candidate yet, because partitioning covers the full space of possible topics from startup (§2.1).
* **Relation to deduplication.** None: `intake` does not enter the Topic Registry (§3.7.6) and takes no part in the neighborhood check. The practical consequence is that a node that mints an emergent topic semantically close to "receiving generic requests" **will not** collapse against `intake`—the Spawner will treat it as a new niche. It is acceptable because `intake` does not compete for work: it is an entry destination, not a specialty.
* **Its name is contract, not configuration.** `intake` is fixed like the rest of the table: no Global Configuration parameter redefines it (§2.3), and nothing about this topic is provisioned with the deployment beyond the convention itself (§5.1). It is the only one in the table that *could* have been configurable—the others are claimed by a structural component through deterministic routing, or emitted by a mechanism that does not consult configuration to name them—but the name takes part in no decision of the network: it carries no weight in deduplication (*relation to deduplication*, above), and the award is resolved by `task_embedding` and never by the topic's name (§3.7.5). A deployment that needs to isolate its topics from those of another network on the same substrate has that problem over the whole table and not over this row: the Bus's namespace solves it (§3.6.5).
